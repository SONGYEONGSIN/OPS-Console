# 업무 지식망 — 저장소와 열람 화면 설계

> 범위: 지식망 4개 서브시스템 중 **(a) 저장소 · (b) 열람 화면**.
> (c) 에이전트가 지식으로 답하기 · (d) 자동학습은 이 문서 밖 — §8·§9 참조.

## 한 줄 요약

업무 지식의 **원본은 마크다운 파일**(옵시디언 볼트)이고, **SharePoint에 둔다**. 회사 PC의 에이전트는 로컬 파일로 직접 읽고 쓰고, 웹(Vercel)은 Graph API로 같은 파일을 읽어 읽기 전용으로 비춘다. 검색은 별도 인덱스가 담당한다.

---

## 1. 전제 — 정해진 것과 확인된 것

**사용자가 정한 것**

- 지식 원본은 **파일**(옵시디언 볼트). Supabase 테이블도, 이 레포의 `docs/`도 아니다
- 에이전트는 **Claude 구독 + Agent SDK**로 회사 PC에서 돈다
- (a)+(b)를 먼저 만든다
- **볼트는 기존 `운영부` 문서고 하위**에 둔다 — 접근 권한이 운영부 범위로 이미 정해져 있다
- **운영자 전원이 쓴다** — 지정 작성자를 두지 않는다. §3.1이 이 결정의 결과를 다룬다

**조사로 확인한 것**

| 사실 | 근거 | 설계에 미치는 영향 |
|---|---|---|
| **이 레포는 PUBLIC이다** | `gh repo view` → `visibility: PUBLIC` | **볼트를 이 레포에 둘 수 없다.** §2 전체가 여기서 갈린다 |
| SharePoint Graph 연동이 이미 있다 | `SHAREPOINT_DRIVE_ID` + `lib/microsoft/{auth,drive-upload,workbook-session}` | 새 인증·새 저장소를 만들지 않아도 된다 |
| 회사 PC 폴러 패턴이 있다 | `scripts/moa-ratio/poll-local.ps1` + `*_requests` 큐 | 동기화·인덱싱 잡을 얹을 자리가 이미 있다 |
| 기존 서술 지식 규모 | `docs/` 99파일 47,914줄 + `.claude/memory/` 49파일 + CLAUDE.md 204줄 | 대략 20~35만 토큰. `knowledge-system-design.md` §4의 "말뭉치 <500K 토큰이면 CAG가 RAG를 이긴다" 기준 **안쪽** — 지금 임베딩을 살 이유가 없다 |

## 2. 볼트를 어디에 두나 — PUBLIC 레포가 답을 좁힌다

사내 업무 지식에는 고객사명·사고 이력·단가·담당자가 들어간다. 공개 레포에 커밋하면 되돌릴 수 없다(git 히스토리에 남는다). 그래서 **이 레포는 후보에서 빠진다.**

| 안 | 원본 위치 | 옵시디언 | 에이전트(회사 PC) | 웹(Vercel) | 판정 |
|---|---|---|---|---|---|
| **A. SharePoint** | SharePoint 문서고 | OneDrive 동기 폴더를 볼트로 열면 그대로 편집 | 로컬 동기 파일을 **파일 도구로 직접** 읽고 씀 | **Graph API로 읽음** — 이미 있는 연동 | **권장** |
| B. 별도 private 레포 | GitHub private | obsidian-git 플러그인 | 로컬 클론, commit·push | GitHub API(토큰) | 가능하나 부품이 늘고, 웹에서 보려면 push를 기다려야 함 |
| C. Supabase Storage | 오브젝트 스토리지 | 직접 못 엶 — 동기 도구를 새로 만들어야 함 | API 경유 | 바로 읽음 | 옵시디언이 원본을 직접 못 다뤄 "파일 원본" 전제가 깨짐 |

### A를 고르는 이유

1. **새 인증·새 저장소가 없다.** `sharePointConfig()`·`getGraphToken()`·드라이브 읽기가 이미 돌고 있다. 볼트용 폴더 ID 하나만 추가된다
2. **옵시디언이 원본을 그대로 다룬다.** OneDrive 동기 폴더를 볼트로 지정하면 평소처럼 로컬 파일을 편집하고, 동기는 OneDrive 클라이언트가 한다
3. **에이전트가 파일 도구를 그대로 쓴다.** Agent SDK의 Read/Write/Edit/Glob/Grep이 로컬 경로에 그대로 붙는다 — 이게 파일 원본을 고른 이유였다
4. **권한이 SharePoint에 있다.** 사내 문서 접근 통제를 새로 만들지 않는다

### A의 약점 — 정직하게

- **동기 지연.** 옵시디언 편집 → OneDrive 동기 → Graph에서 보임까지 수 초~수십 초. 열람 화면이 "방금 쓴 글이 아직 안 보임"을 겪을 수 있다. 실시간 협업 편집이 아니므로 감수한다
- **충돌.** 사람과 에이전트가 같은 파일을 동시에 쓰면 OneDrive가 충돌 사본을 만든다. §7에서 다룬다
- **Graph 반영 지연은 이미 겪은 문제다.** 공문관리대장 디버깅(2026-08-14)에서 워크북 세션 쓰기가 파일에 반영되기까지 1~2분 걸리는 것을 실측했고, 그걸 모른 채 "저장 안 됨"으로 오진했다. 파일 업로드는 워크북과 경로가 다르지만, **"쓴 직후 읽어서 확인"하는 검증 방식은 여기서도 쓰지 않는다**

## 3. 볼트 구조 — 분류는 "누가 사실을 판정하나"를 따른다

참고 시스템의 분류(`상태 / 개념 / 맥락 팩 / 결정 / 엔티티 / 오류 사례 / harnesses / 플레이북 / 프로젝트`)를 그대로 베끼지 않는다. `knowledge-system-design.md` §2가 세운 원칙 — **사실 판정은 코드(L0)만, 문서는 배경 설명만** — 을 지키는 분류여야 한다.

```
vault/
├── 개념/        용어·도메인 개념 ("원서접수란", "미수채권 경과일수")
├── 플레이북/    절차 ("경위서 발송하는 법", "백업 요청 보내는 법")
├── 규칙/        지켜야 하는 제약·합의된 예외 (§10 실험이 요구해 추가)
├── 결정/        왜 그렇게 했나 (ADR — 되돌릴 때 근거가 된다)
├── 오류사례/    무엇이 어떻게 터졌고 무엇을 고쳤나
├── 엔티티/      대학·서비스·거래처 배경 (사실이 아니라 맥락)
├── 프로젝트/    진행 중 작업의 맥락
└── 제안/        에이전트가 쓴 초안 — 사람이 승인해야 위로 올라간다 (§7)
```

**의도적으로 뺀 것**: `상태`. 상태는 L1(운영 실데이터)이고 Supabase가 답한다. 파일에 상태를 적으면 즉시 낡고, 낡은 상태를 근거로 답이 나간다.

### 분류 판별 — 헷갈릴 때의 한 문장

| 분류 | 판별 |
|---|---|
| **개념** | 이걸 모르면 대화가 안 통하는 **용어**인가 |
| **플레이북** | 읽고 나서 **따라 하면 되는** 절차인가 |
| **규칙** | 우리가 고른 게 아니라 **지켜야 하는** 제약·합의인가 |
| **결정** | 나중에 "왜 이렇게 했지?"라고 물을 **우리의 선택**인가 |
| **오류사례** | 실제로 **터진 일**과 그 수습인가 |
| **엔티티** | 특정 대학·서비스·거래처의 **배경**인가 |
| **프로젝트** | 지금 **진행 중**이라 끝나면 낡을 맥락인가 |

`규칙`과 `결정`이 가장 헷갈린다. 가르는 말은 **주어**다 — 우리가 정했으면 `결정`, 외부와 합의했거나 도구가 강제하면 `규칙`.

각 문서 앞에 frontmatter를 둔다 — 열람 화면의 트리·검색·신선도 표시가 전부 여기 의존한다:

```yaml
---
title: 경위서 발송 절차
category: 플레이북
updated: 2026-08-14
owner: 송영신
related: [사고보고, 공문관리대장]
---
```

### 3.1 전원이 쓴다 — 형식은 강제할 수 없다, 드러낼 수 있을 뿐

작성 도구가 옵시디언이라 **우리 코드가 저장을 가로챌 수 없다.** frontmatter를 빠뜨린 문서, 분류를 안 정한 문서, 6개월 넘게 안 고친 문서는 반드시 생긴다. 지정 작성자를 두지 않기로 한 이상 이건 예외가 아니라 기본값이다.

그래서 **막지 않고 드러낸다** — 세 층위로:

| 층위 | 무엇 | 왜 |
|---|---|---|
| **옵시디언 템플릿** | 새 문서 생성 시 frontmatter가 채워진 틀이 뜬다 | 대부분은 여기서 해결된다. 비용 0 |
| **인덱스 검사** | 인덱스 잡이 `title`·`category`·`owner` 누락을 기록한다 | 누락을 **세어야** 문제인지 아닌지 안다 |
| **열람 화면 표시** | 형식 미비 문서를 `미분류`로 모아 보여준다 | 안 보이면 아무도 안 고친다 |

**막지 않는 이유**: frontmatter가 없다고 인덱싱에서 빼면, 애써 쓴 지식이 화면에서 사라진다. 지식을 잃는 것보다 형식이 어긋난 채 보이는 게 낫다. `미분류`는 버리는 칸이 아니라 **고칠 목록**이다.

**owner를 두는 이유**: 전원이 쓰면 같은 주제가 여러 번 쓰인다. 누가 썼는지 보여야 합칠지 물어볼 사람이 정해진다.

## 4. 열람 화면 (b)

`/dashboard/knowledge` — 좌측 트리 + 검색, 우측 문서 뷰어. **읽기 전용.** 편집은 옵시디언에서 한다.

- **표준 인스펙터·목록 패턴을 쓰지 않는다.** 이건 목록+상세가 아니라 문서 탐색이다. 참고 화면처럼 트리+뷰어 2단이 맞다
- 마크다운 렌더 + frontmatter의 `updated`·`owner`를 문서 머리에 표시
- `related`는 클릭 가능한 링크로 — 지식망의 "망"이 여기서 보인다
- **신선도 경고**: `updated`가 6개월 이상 지난 문서는 상단에 표시한다. 낡은 지식을 낡은 줄 모르고 읽는 게 가장 나쁘다

---

## 5. 검색 — 인덱스가 필요한 이유

Graph API로 파일을 매 검색마다 훑으면 느리고 호출량이 많다. 마크다운 **본문** 검색은 더 약하다.

**인덱스 잡**: 회사 PC 폴러(또는 서버 cron)가 주기적으로 볼트를 훑어 `knowledge_docs` 테이블에 `path · title · category · owner · updated · body · content_hash`를 넣는다. 변경분만 갱신한다(`content_hash` 비교).

- 웹 검색·트리는 **인덱스만** 읽는다 → 빠르고 Graph 호출이 없다
- 문서 본문 표시도 인덱스에서 — Graph 왕복이 사라진다
- **원본은 여전히 파일이다.** 인덱스는 사본이고, 갈라지면 파일이 이긴다
- 기존 `searchAllDomains`에 도메인 하나로 등록하면 어시스턴트가 (c) 단계에서 그대로 쓴다

---

## 6. 기존 지식과의 관계

`docs/`(4.8만 줄)와 `.claude/memory/`(49파일)는 **개발 harness의 지식**이고, 볼트는 **운영 업무의 지식**이다. 섞지 않는다.

- `docs/superpowers/specs/*` — 설계 이력. 개발자가 읽는다. 레포에 남는다
- `.claude/memory/*` — 세션 간 기억. 에이전트가 읽는다. 레포에 남는다
- **볼트** — 운영자의 업무 지식. 사람과 운영 에이전트가 읽는다. SharePoint

겹치는 것을 옮기는 이관 작업은 이 설계 밖이다. 볼트가 서면 그때 판단한다.

## 7. 사람과 에이전트가 같은 파일을 쓸 때

(d) 자동학습에 가서야 실제 문제가 되지만, 구조를 지금 정해둔다.

- **에이전트는 사람 문서를 고치지 않는다.** 에이전트가 쓰는 것은 `제안/` 하위에만 들어간다
- 사람이 읽고 승인해서 본 위치로 옮긴다. 옮기는 것은 사람이 옵시디언에서 한다
- 이러면 OneDrive 충돌 사본이 구조적으로 안 생기고, (d)의 "검증 없는 자동학습이 오류를 증폭한다" 문제도 같은 장치로 막힌다

---

## 8. (d) 자동학습을 지금 하지 않는 이유

자동으로 쌓인 지식이 틀리면, 그걸 근거로 답이 나가고, 그 답이 다시 쌓인다. **오류가 증폭되는 고리**다. 그래서 (d)는 §7의 `제안/` + 사람 승인 게이트가 선 뒤에만 착수한다.

그리고 **읽을 게 없으면 학습할 것도 없다.** (a)(b)로 사람이 지식을 쌓기 시작해야 (d)가 무엇을 배워야 하는지 알 수 있다.

## 9. 단계

### 0단계 — 볼트를 세운다 (코드 0줄)
SharePoint에 볼트 폴더를 만들고, OneDrive 동기 폴더를 옵시디언 볼트로 연다. §3 분류로 디렉토리를 만들고 **문서 10개를 손으로 쓴다**.
- **완료 조건**: 운영자 한 명이 옵시디언에서 문서를 쓰고, 다른 PC에서 그 문서가 보인다. 그리고 §10 판정을 사람 손으로 한 번 더 통과한다
- **하지 말 것**: 코드 작성. 기존 `docs/` 대량 이관

### 1단계 — 인덱스
볼트 → `knowledge_docs` 동기 잡. 변경분만.
- **완료 조건**: 볼트에 문서를 추가하면 다음 주기에 인덱스에 나타난다. 삭제도 반영된다. frontmatter 누락 건수가 집계된다
- **하지 말 것**: 검색 품질 튜닝. 지금은 존재만 확인

### 2단계 — 열람 화면
`/dashboard/knowledge` 트리 + 검색 + 뷰어 + 신선도 표시.
- **완료 조건**: 사이드바에서 들어가 문서를 찾아 읽을 수 있고, `related` 링크로 옮겨 다닐 수 있다
- **하지 말 것**: 편집 기능. 편집은 옵시디언이 한다

### 3단계 (조건부) — 어시스턴트가 볼트를 읽는다
`searchAllDomains`에 knowledge 도메인 추가. **0~2단계로 문서가 30개 이상 쌓인 뒤에만** 착수한다 — 10개짜리 볼트를 검색에 붙여도 답이 나아지지 않는다.

## 10. 가장 싼 첫 실험 — 실행함 (2026-08-15)

**실험: 분류가 실제 지식을 담는가**

- **무엇을**: 레포·메모리에 남아 있는 **실제 업무 지식 10개**를 분류에 넣어본다
- **성공 판정**: 10개가 모두 하나의 칸에 **망설임 없이** 들어간다
- **실패 판정**: 2개 이상이 애매하면 분류가 틀린 것

### 결과 — 7개 즉시, 3개 애매 → **실패, 분류를 고쳤다**

| 지식 | 결과 |
|---|---|
| 경위서 발송 절차 / 백업 요청 그룹별 발송 / 팀 브리핑 발행 절차 | 플레이북 — 즉시 |
| 시행번호 채번 규칙 / `MAIL_DRY_RUN` 안전장치 | 개념 — 즉시 |
| Graph 워크북 반영 1~2분 지연 | 오류사례 — 즉시 |
| GAS 미수채권을 OPS-Console로 이전한 이유 | 결정 — 즉시 |
| **공문대장 F열 하이퍼링크 형태 + 255자 제한** | **애매** |
| **연세대 서울 수시 1차 예외 (마감 17시·18시 공개가 정상)** | **애매** |
| **이이화 자동 CC 금지** | **애매** |

애매한 셋은 **같은 종류**였다 — "특정 대상에 대해 지켜야 하는 규칙". 용어(개념)도, 절차(플레이북)도, 우리의 선택(결정)도, 배경(엔티티)도 아니다. 셋 중 둘은 터진 적조차 없어 오류사례도 아니다.

**→ `규칙/` 칸을 추가했다.** 셋이 모두 거기로 들어가고 나머지 7개는 그대로다. 규칙은 낡지 않고 사실 판정도 하지 않아(코드가 판정하는 L0를 침범하지 않아) §2 원칙에 어긋나지 않는다.

### 남은 검증

이 실험은 **레포에 남은 지식**으로 돌렸다. 운영자 머릿속 지식은 분포가 다를 수 있으므로, §9 0단계에서 사람이 직접 10개를 쓸 때 같은 판정을 한 번 더 한다 — 그때도 2개 이상 애매하면 분류를 다시 본다.
