# 우편물 > 영수증 출력 — 전표에 붙일 A4 를 손 대신 만든다

**질문**: 우편 영수증을 내부 전표 증빙으로 붙이는 일을 화면에서 끝낼 수 있는가 — A4 배치와 형광펜까지.
**날짜**: 2026-09-28

---

## 1. 한 줄 결론

**판독이 이미 사진을 Claude 로 읽고 있으니, 같은 판독에서 금액·일자·종이 테두리의 위치까지 받으면 된다.** 서버가 그 위치로 사진을 잘라 형광펜을 입히고 A4 PDF 에 3개씩 놓는다. 회사 PC 폴러와 DB 스키마는 바뀌지 않는다 — 프롬프트는 서버가 만들고, 판독 결과는 이미 jsonb 로 저장된다.

---

## 2. 지금

- 내부 전표를 쓸 때 영수증을 A4 에 **손으로 붙이고** 형광펜으로 접수일자·총요금을 칠한다. 올라온 영수증 14장 모두 사진에 손 형광펜 자국이 찍혀 있다.
- 우편물 메뉴에 영수증 사진이 있다 — 비공개 버킷 `postal-receipts`, JPG/PNG/HEIC/WebP, 10MB(`features/postal/upload-guard.ts`).
- 판독은 회사 PC 폴러(`scripts/postal/extract-local.mjs`, Agent SDK 의 `Read`)가 하고, 프롬프트는 서버(`features/postal/extract-prompt.ts`)가 만든다. 결과는 `postal_extract_requests.result`(jsonb). **금액·일자의 값은 있고 위치는 어디에도 없다.**
- 목록(`PostalTable`)에 선택·일괄 동작이 없고, 인쇄 기능도 없다.

## 3. 확정 입력 (사용자 결정 2026-09-28)

| 항목 | 결정 |
|---|---|
| 음영 위치 | 영수증 **사진 위**, 값이 찍힌 자리에 형광펜처럼 |
| 칠하는 곳 | `접수일자` 값, `총요금` 값 — 항목명(`접수일자 :`)은 칠하지 않는다 |
| 배치 | A4 세로, **한 줄에 최대 3개**(칸 59mm). 두 줄로 쌓지 않는다 — 긴 영수증이 있다 |
| 출력 | PDF, 새 탭 |
| 한 번에 | PDF 하나에 30장까지. 넘으면 접수일시 순으로 30장씩 나눈 PDF 여러 개 |
| 대상 | 사진이 있는 영수증 전부(확정 여부 무관) |
| 순서 | 접수일시 오름차순 — 전표에 붙는 순서 |
| 총요금 형광펜 | **한 줄 위까지 넓혀 칠한다(두 줄 폭)** — 판독이 총요금 상자를 0~1줄 아래로 짚는다(§4.1). 같은 금액이 적힌 옆 줄이 함께 칠해질 수 있다 (2026-09-29) |
| 회전 정보가 붙은 폰 사진 | **업로드 때 픽셀째 세워 저장한다** — 판독 모델이 회전 정보를 무시한다(§4.1, §5.5) (2026-09-29) |

## 4. 실측 (스파이크, 2026-09-28)

- 영수증 14장 전부 JPG 3024×4032, EXIF 회전 없음. **사진 폭의 약 40% 가 배경(책상)** 이다 — 자르지 않고 3열에 넣으면 영수증 글씨가 너무 작다.
- Claude 가 사진을 보고 낸 비율 좌표로 사각형을 그렸더니 손 형광펜 자리(접수일자·총요금)와 **겹쳤다.** 형광펜이 없는 칸(접수번호·승인금액)에서도 글자에 맞았고, 살짝 기운 사진도 축 정렬 사각형으로 충분했다.
- 3열 견본(칸 59mm)에서 영수증 글씨가 읽힌다. 영수증 한 장이 A4 높이의 약 절반이고, 칸 폭 59mm 면 등기 20건 안팎까지 줄이지 않고 들어간다.
- **한계**: 스파이크의 좌표는 이 대화의 모델이 낸 것이다. 폴러의 실제 모델로 확인한 결과는 §4.1.
- sharp(0.35, libvips 8.18)는 **HEIC 를 못 읽는다** — heif 입력이 `.avif` 뿐이다. 지금 14장은 전부 JPG.

### 4.1 폴러 모델 실측 (PR-1 머지 전 로컬, 2026-09-28)

폴러와 같은 Agent SDK 옵션으로 이 PC 에서 직접 판독했다(큐·DB 쓰기 없음). 14장 중 7장을 돌렸고(메모리 부족으로 중단), 1장은 3분 제한을 넘겼다.

| 상자 | 결과 |
|---|---|
| 종이(`receipt`) | 6/6 종이 전체 |
| 접수일자 값 | 6/6 정확 |
| 총요금 값 | 3/6 정확, **3장은 바로 아래 '수납요금' 줄** |
| 판독 값(등기번호·요금) | 6/6 이전 판독과 같음 — 위치를 얹어도 나빠지지 않았다 |

- 총요금 오차는 **전부 아래쪽**, 0~1줄이다(줄 간격 ≈ 사진 높이의 1.9%). 상자의 가로 범위는 '(즉납)' 줄을 겨냥했다 — 줄을 헷갈린 게 아니라 세로 정밀도다.
- 프롬프트를 보강해도('총 요 금' 항목명과 같은 줄, 그 글자 높이) 좌표가 0.002 안쪽으로 그대로였다. 지시로는 안 고쳐진다.
- **회전 정보**: 사진을 옆으로 눕히고 회전 정보(EXIF orientation 6)를 붙인 사본은 크기(4032×3024·1600×1200)와 상관없이 **누운 픽셀 좌표계**로 왔다. 모델은 회전 정보를 적용하지 않는다. 누운 사진에서는 총요금 상자가 더 크게 빗나갔다.

## 5. 설계

### 5.1 위치 — 판독에 얹는다

- 프롬프트에 `regions` 를 요청한다. 상자는 셋이다.
  - `receipt` — 영수증 종이 전체(잘라내기용)
  - `accepted_at` — 접수일자 **값**(예: `2026-09-23 15:14`)
  - `total_fee` — 총요금 **값**(`(즉납)` 포함, 예: `(즉납) 17,400원`)
- 좌표는 `[x0, y0, x1, y1]`, 사진 왼쪽 위 기준 0~1 비율. 안 보이면 null.
- 스키마(`extract-parse.ts`)에서 `regions` 는 선택이다. **상자 하나가 이상하면(범위 밖·뒤집힘·숫자 아님) 그 상자만 null** 로 둔다 — 기존 필드처럼 `.catch(null)`. 판독 전체는 살린다. 형광펜보다 금액·등기번호가 중요하다.
- 저장은 `postal_extract_requests.result` 그대로다. 마이그레이션도 폴러 수정도 없다.
- **기존 14장**은 PR-1 배포 후 판독 요청을 한 번씩 넣는다(일회성 스크립트, 커밋하지 않음). 확정된 영수증은 확정·전도금·등기 항목이 바뀌지 않는다 — 그것을 쓰는 곳은 확정 버튼(`extract-actions.ts:121-140`) 하나뿐이다. 목록에 보이는 값만 새 판독으로 바뀐다. 대기·진행 중 요청이 있는 영수증은 건너뛴다(그 요청이 새 요청을 막는다).

### 5.2 화면 — 우편물 > 영수증 목록 (`PostalTable`)

- 행 왼쪽에 체크박스. 행 클릭은 검토 열기라서(`PostalTable.tsx:241`) 체크박스 클릭은 전파를 막는다.
- 제목(`영수증`) 옆에 `HeaderActionButton` **[영수증 출력 (N)]**. 0장이면 비활성.
- 30장 이하면 버튼 하나 → 새 탭. **30장 초과면** 그 자리에 [1~30장 PDF] [31~45장 PDF] … 처럼 접수일시 순으로 나눈 묶음 버튼을 놓는다.
- 고른 것 중 형광펜 위치를 다 찾지 못한 장수를 버튼 옆에 적는다 — "3장 중 1장은 형광펜이 빠진 곳이 있습니다". 하나만 잡힌 영수증도 여기에 센다(잡힌 한 곳은 칠한다). **PDF 에는 안내 문구를 찍지 않는다** — 전표에 붙는 종이다.
- `getExtractStates`(`features/postal/queries.ts`)가 영수증별 `hasRegions` 를 함께 돌려준다. 형광펜 두 상자(`accepted_at`·`total_fee`)가 다 있을 때만 참이다.

### 5.3 PDF — `GET /api/postal/receipts/pdf?ids=…`

- **가드**: 로그인(proxy) + `canViewMenu("postal", me)` — 페이지(`requireMenu("postal")`)와 같은 판정을 쓴다. 두 벌이면 한쪽만 바뀐다.
- **입력**: `ids=<uuid>,<uuid>,…` 쉼표로 잇는다. uuid 1~30개, 중복 제거. 형식이 틀리거나 31개 이상이면 400.
- 영수증과 최신 판독 결과(regions, accepted_at)를 읽어 접수일시 순으로 정렬한다(판독 전이면 올린 시각).
- **한 장씩 순서대로**(메모리 때문에 병렬로 하지 않는다):
  1. 저장소에서 받는다.
  2. sharp `rotate()` — EXIF 방향을 반영한다. 업로드가 사진을 세워 저장하므로(§5.5) 회전 정보가 남은 사진은 그 전에 올린 것뿐인데, 그 판독 좌표는 누운 픽셀 기준이라(§4.1) **위치를 쓰지 않는다** — 자르기·형광펜 없이 세워서 싣는다.
  3. `receipt` 상자에 사방으로 사진 폭·높이의 2% 여유를 더해 자른다. 사진 밖으로 나가는 부분은 경계에서 자른다.
  4. 인쇄 해상도로 줄인다(칸 59mm ≈ 200dpi).
  5. `accepted_at`·`total_fee` 상자에 노랑 형광펜을 **곱하기 합성**으로 입힌다 — 글자가 그대로 검게 비친다. 상자 높이의 25% 여유, 둥근 모서리. **총요금은 상자 높이만큼 위로 넓힌다**(두 줄 폭, §4.1) — 여유는 원래 상자 높이 기준.
  6. JPEG 로 굽는다.
- **위치 없음**: 없는 상자만큼만 빠진다 — `receipt` 가 없으면 자르지 않고 사진 전체를 칸에 맞추고, 형광펜 상자가 없으면 그 자리만 안 칠한다.
- **못 읽음**(다운로드 실패·HEIC·손상): 그 칸에 사유 한 줄을 적는다. 나머지는 정상 출력한다 — 한 장 때문에 전체가 실패하지 않는다.
- **react-pdf**: A4 세로, 여백 10mm, 칸 3개(59mm)에 간격 6mm, 한 페이지 한 줄. 페이지 가용 높이보다 긴 영수증은 높이에 맞춰 줄인다. 아래 가운데에 쪽번호만 둔다(머리글 없음 — 영수증 자리를 줄이지 않는다). 폰트는 기존 PDF 와 같은 방식으로 Pretendard 를 등록한다.
- **응답**: `application/pdf` inline, 파일명 `우편영수증_{첫 접수일}_{끝 접수일}.pdf`(같은 날이면 날짜 하나, 판독 전 영수증은 올린 날로 센다).

### 5.4 나누기

- 묶음은 **화면**이 계산한다(목록에 접수일시가 있다). 서버는 요청 하나에 30장 이하만 받는다 — 경계가 서버에 있으니 화면이 틀려도 넘치지 않는다.
- 30 은 시작값이다. PR-2 에서 30장 처리 시간과 메모리를 재서 여유가 있으면 키운다. 상수 하나(`RECEIPT_PDF_BATCH`)를 화면과 서버가 같이 쓴다.

### 5.5 업로드 — 사진을 바로 세워 저장한다 (2026-09-29)

- `uploadReceipt`(`features/postal/actions.ts`)가 저장 전에 `uprightPhoto` 를 거친다. 회전 정보가 1 이 아닌 **JPEG 만** 픽셀째 세워 다시 굽는다(품질 92, 메타데이터 없음 — 회전 정보가 사라진다). 그러면 판독 모델·검토 화면·PDF 가 같은 픽셀을 본다(§4.1).
- 그 밖은 받은 그대로 저장한다 — 이미 바로 선 JPEG, JPEG 가 아닌 사진, sharp 가 못 읽는 사진(HEIC 등). 다시 굽지 않는다(화질). HEIC 는 지금처럼 판독은 되고 출력은 그 칸에 사유를 적는다.
- 머리는 JPEG 인데 픽셀을 못 푸는 사진은 업로드를 거절한다 — "사진을 읽지 못했습니다 — 다시 찍어 올려 주세요". 판독·화면·출력 어디서도 못 쓴다.
- 이미 올라온 14장은 회전 정보가 없다(§4) — 옮길 것이 없다.

## 6. 안 하는 것

- 형광펜 위치를 손으로 고치기 — 틀리면 '다시 추출'. 틀리는 일이 잦으면 그때 만든다.
- 총요금 형광펜을 한 줄에 딱 맞추기(글자 줄 탐지·OCR·확대 재판독) — 두 줄 폭으로 써 보고 모자라면 그때 정한다.
- 30장이 넘을 때 PDF 하나로 합치기 — 백그라운드로 나눠 만들어 합치는 구조가 필요해 커진다.
- HEIC 변환, 두 줄 배치, 전체 선택, 영수증 아래 금액·일자 글씨.
- 전도금·등기대장 흐름 변경.
