# SMS 발신번호 사전등록 신청 알림 메일

## 1. 왜

운영자는 Teams '어플라이사업본부' 팀 > '내부관리자' 채널 상단 탭의 Microsoft Lists 목록 **'SMS 발신번호 사전등록 신청'** 에 신청 행을 넣는다. 담당 매니저가 처리를 끝내면 그 행의 상태를 '요청' → '완료'로 바꾼다.

이 목록은 아무에게도 알리지 않는다. 담당 매니저는 탭을 열어 보기 전까지 새 신청을 모르고, 신청한 운영자도 '완료'로 바뀐 걸 들어가 보기 전까지 모른다. Teams 자체 기능(목록 규칙·Workflows)으로 메우려 했으나, 사용자가 OPS-Console 자체 개발을 택했다(2026-11-03).

## 2. 목표 · 비목표 · 반목표

**목표**
- 새 신청 행이 생기면 **5분 안에** 담당 매니저에게 메일이 간다.
- 행의 상태가 '완료'로 바뀌면 **5분 안에** 그 행을 만든 운영자에게 메일이 간다.
- 운영자·담당 매니저의 작업 방식은 지금과 똑같다(신청은 Teams 목록, 처리 표시도 Teams 목록).

**비목표**
- 신청 화면을 OPS-Console 로 옮기기. 내부관리자 메뉴는 지정자 전용이라 운영자 전원이 신청할 자리가 아니다.
- Teams 메시지 알림(사용자 결정: 메일).
- 첨부 파일 읽기·전달, ServiceID 를 `closing_services` 와 대조하기, '반려' 같은 다른 상태 흐름, 목록에 쓰기.
- OPS-Console 화면(목록·이력 화면). 실행 결과는 자동화 페이지 실행 로그로 본다.

**반목표** (기술적으로 돌아가도 실패인 것)
- 처음 켤 때 기존 32행(완료 27건)으로 메일이 쏟아진다.
- 같은 행에 같은 종류의 메일이 두 번 간다 — 5분마다 도는데 '이미 보냈다'를 잊거나, 완료→요청→완료로 되돌렸다 다시 바꿀 때.
- 조용히 멈춘다 — cron 미등록·env 누락·Graph 오류가 실행 로그·실패 알림·일일 보고 어디에도 안 나타난다. '알림이 안 간다'는 지금 문제를 다른 모양으로 다시 만드는 것이다.
- `[운영부 상황실]` 브랜드로 나간다(사용자: 내부관리자 채널 일이라 분리).

| 항목 | 결정 |

| 알림 수단 | 메일 (Teams 메시지 아님) |
| 새 신청 알림 | **담당 매니저 본인 메일함 → 본인**. 미수채권 운영자 알림과 같은 방식(`operator-mail-actions.ts` 의 `senderUserId === toEmail`) |
| 새 신청 제목 | `[내부관리자] SMS 발신번호 사전등록 신청 — {대학명}` |
| 완료 알림 | 보낸다. 받는 사람은 그 행을 만든 운영자 |

## 4. 원천 (실측 2026-11-03)

- 목록은 그룹 루트 사이트 `/sites/ApplyService2` 에 있다. 이 사이트는 내부관리자 현황 파일을 읽는 `SHAREPOINT_DRIVE_ID` 드라이브의 사이트와 같다.
- **이름으로 찾지 않는다.** '어플라이사업본부' 그룹이 2개, 비슷한 이름의 사이트가 3개 나온다. 사이트 id·목록 id 를 env 로 둔다.
- 현재 앱 토큰(client credentials)에 `Sites.ReadWrite.All`·`Mail.Send`·`User.Read.All` 이 있다. **권한 추가 없음.**
- 항목 32건(요청 5 · 완료 27), 한 페이지(200개)에 다 들어온다.

| 표시 이름 | `fields` 키 | 타입 | 값 |
|---|---|---|---|
| 제목 | `Title` | text | |
| 상태 | `_xc0c1__xd0dc_` | choice | `요청`, `완료` |
| 대학명 | `_xb300__xd559__xba85_` | text | |
| 구분 | `_xc0ac__xc774__xd2b8__xad6c__xbd` | choice | `접수`, `접수+PIMS`, `PIMS` |
| ServiceID | `UnivID` | **text** | |
| 첨부 파일 | `Attachments` | boolean | |

- 제목·상태·대학명·구분·ServiceID 다섯 열은 목록 설정에서 **필수**다(실측 32/32 채워짐). 그래서 이 키가 없는 행은 사람이 비워 넣은 신청이 아니라 목록 형식이 바뀐 것이다 — §5-4.

- 내부 이름은 표시 이름을 바꿔도 그대로라 상수로 둔다(구분 열 키는 원래 이름 인코딩이 32자에서 잘린 것이다 — 오타가 아니다).
- 신청자: 항목의 `createdBy.user.email` (32/32 채워짐), 표시 이름은 `createdBy.user.displayName`.
- 항목 링크: 항목의 `webUrl`.
- **상태로 서버 쪽 `$filter` 를 걸지 않는다.** 인덱스 없는 열이라 `Prefer: HonorNonIndexedQueriesWarningMayFailRandomly` 헤더가 필요하고, 이름 그대로 무작위로 실패할 수 있다. 전량을 읽어 코드에서 거른다.

## 5. 동작

### 5-1. 감지: 전량 읽기 + 스냅샷 대조

5분마다 목록 항목 전체를 읽어(`/sites/{site}/lists/{list}/items?$expand=fields`, nextLink 는 Graph 호스트일 때만 따라간다 — 내부관리자 `source.ts` 와 같은 규칙) DB 스냅샷과 비교한다.

- **새 행** = 스냅샷에 없는 항목 id → 새 신청 메일.
- **완료 전환** = 지금 상태가 `완료` 이고 그 행의 완료 메일을 아직 안 보냈다 → 완료 메일.
- 그 밖의 변화(제목·대학명 수정, 행 삭제, 다른 상태값)는 메일을 만들지 않는다. 스냅샷의 상태만 갱신한다.

delta(`items/delta`)는 동작하지만 고르지 않았다(설계자 판단): deltaLink 를 DB 에 보관하고 만료(410) 시 전체를 다시 읽는 경로가 따로 필요하다. 32행이면 전량 대조가 더 단순하고 같은 결과다.

### 5-2. 처음 켤 때: 시드

스냅샷 표가 **비어 있으면** 그 실행은 메일을 보내지 않고 지금 있는 모든 행을 적재만 한다. 실행 메시지에 `처음 실행 — 기존 32행 적재, 발송 없음` 처럼 드러낸다.

- 모든 행: 새 신청 알림 = `seeded`.
- 이미 `완료` 인 행(27건): 완료 알림 = `seeded`.
- 아직 `요청` 인 행(5건): 완료 알림 = **`pending`** — 지금 처리를 기다리는 신청자도 매니저가 '완료'로 바꾸면 메일을 받는다(목표 2). 막아야 하는 것은 이미 끝난 27건이 한꺼번에 나가는 일뿐이다.

- 그 결과 배포와 첫 실행 사이 몇 분 안에 들어온 신청은 알림 없이 적재된다. 받아들인다(설계자 판단) — 기존 '요청' 5건과 같은 처지이고, 첫 실행을 배포 직후 수동으로 돌리면 그 틈이 거의 없다.
- 이후 표가 비는 일(누가 행을 다 지움)은 없다고 본다. 스냅샷 표는 service_role 만 쓴다.

### 5-3. 메일 두 종류

| | 새 신청 | 완료 |
|---|---|---|
| 보내는 메일함 (`senderUserId`) | 담당 매니저 | 담당 매니저 |
| 받는 사람 (`toEmail`) | 담당 매니저 | 행의 `createdBy.user.email` |
| 제목 | `[내부관리자] SMS 발신번호 사전등록 신청 — {대학명}` | `[내부관리자] SMS 발신번호 사전등록 완료 — {대학명}` |
| 본문 | 대학명 · 구분 · ServiceID · 신청자(표시 이름) · 목록 행 링크 | 대학명 · 구분 · ServiceID · 목록 행 링크 + 처리 완료 안내 한 줄 |

- 완료 메일을 담당 매니저 메일함에서 보내는 것은 설계자 판단이다(사용자에게 짐작으로 밝혔고 반대가 없었다). 신청자가 궁금하면 그 메일에 바로 답장할 수 있다.
- 본문은 HTML. 목록 값은 사람이 적은 글이라 **이스케이프**한다. 링크는 `webUrl` 이 `https://` 로 시작할 때만 앵커로 감싼다.
- 본문 끝에 자동 발송 고지 한 줄(`이 메일은 SMS 발신번호 사전등록 신청 목록을 보고 자동으로 보냈습니다.`). `[운영부 상황실]` 문구는 어디에도 넣지 않는다.
- `saveToSentItems` 는 `sendGraphMail` 기본값(true) 그대로 — 매니저 보낸편지함에 남는다.
- 한 행이 처음 보일 때 이미 `완료` 이면(5분 안에 신청하고 처리까지 끝남) 새 신청 메일과 완료 메일을 둘 다 보낸다.

### 5-4. 실패와 재시도

**보내기 전에 먼저 잡는다.** 알림 하나를 보내기 전, 그 칸을 조건부 UPDATE(`pending` 이고 시도 횟수 < 3 일 때만 → `sending`, 시도 +1)로 잡는다. 0행이 갱신되면 다른 실행이 잡은 것이니 건너뛴다. 메일 호출 뒤 `sent`/`failed`/`pending`(재시도 남음)으로 적는다.
- 그래서 실행 둘이 겹쳐도(cron + 수동 실행) 같은 알림이 두 번 가지 않는다.
- 메일은 나갔는데 결과 기록이 실패하면 그 칸은 `sending` 으로 남는다. **`sending` 이 30분 넘게 남은 칸은 그 시도가 실패한 것으로 보고** `pending`(또는 3회면 `failed`)으로 돌린다. 이 경우만 같은 메일이 한 번 더 갈 수 있다 — 누락보다 중복을 택했다(설계자 판단: 이 기능이 고치려는 것이 '알림이 안 간다'이다).

- 메일 하나가 실패하면 그 행의 해당 알림을 '보냄'으로 표시하지 않는다 → 다음 실행이 다시 시도한다.
- **같은 알림은 3번까지만 시도한다.** 3번째도 실패하면 `failed` 로 굳히고 더 시도하지 않는다(5분마다 영원히 실패하며 실패 알림을 반복하지 않게). 시도 횟수와 마지막 오류를 행에 남긴다.
- 신청자 메일이 비어 있으면 완료 알림을 시도하지 않고 바로 `failed`(사유: 신청자 메일 없음). `/users/{id}` 로 보조 조회하지 않는다 — 32/32 채워져 있고, 폴백 경로는 프로젝트 규칙상 두지 않는다.
- 실행 결과 `ok` 는 **그 실행에서 실패가 하나라도 있으면 false**. `recordAutomationRun` 이 첫 실패에 Teams 알림을 보내고, 일일 보고가 이어서 상기시킨다.
- Graph 목록 읽기 실패·env 누락은 그 실행 전체 `ok:false` + 무엇이 없는지 적은 메시지. 스냅샷을 건드리지 않는다.
- 필수 열 키(§4)가 빠진 행은 메일도 스냅샷도 만들지 않고 건너뛰되, **그 실행은 `ok:false`** + `형식이 맞지 않는 행 N건` 을 메시지에 남긴다. 개수만 적고 성공으로 두면 그 신청은 영영 알림 없이 묻힌다. 형식이 고쳐지면 다음 실행이 그 행을 새 행으로 보고 메일을 보낸다(의도한 동작).
- 매니저 메일함 발송이 `403 ErrorAccessDenied` 면 테넌트의 Exchange Application Access Policy 가 그 메일함을 막고 있는 것이다. 코드로 우회하지 않는다 — 실행 로그에 오류가 남고, Exchange 관리자 작업으로 푼다(§9-5).

### 5-5. `MAIL_DRY_RUN`

`MAIL_DRY_RUN=true` 면 Graph 메일 호출 없이 그 알림을 `dry_run` 으로 기록하고 '처리됨'으로 본다(다시 시도하지 않는다). 다른 메일 잡과 같은 판정(`(process.env.MAIL_DRY_RUN ?? "").toLowerCase() === "true"`, 호출하는 쪽에서 본다).

### 5-6. 실행 메시지

`신규 N건 알림 · 완료 M건 알림` (+ `· 실패 K건`), 변화가 없으면 `변화 없음 (32행)`. 사람을 가리키는 값(이름·메일)은 메시지·details 에 넣지 않는다. 대학명과 항목 id 는 넣어도 된다.

## 6. 저장

새 테이블 하나 — 행마다 '무엇을 알렸나' 의 기록. 이름은 builder 판단(예: `sms_sender_request_notices`).

- 키: 목록 항목 id (`text`, 유니크/PK). 같은 행에 같은 알림이 두 번 가지 않는 것을 DB 가 보장한다.
- 마지막으로 본 상태(`요청`/`완료`/그 밖의 문자열).
- 새 신청 알림·완료 알림 각각: 상태(`pending`/`sending`/`sent`/`dry_run`/`seeded`/`failed`), 시도 횟수, 마지막 오류, 잡은 시각(`sending` 진입), 보낸 시각, Graph message id.
- 신청자 메일 주소·이름은 **저장하지 않는다** — 매번 목록에서 읽는다.
- RLS 켜고 정책 없음(service_role 만). 마이그레이션 이름 `YYYYMMDD_snake_case.sql`.

## 7. 실행 경로

- 자동화 registry 잡으로 등록한다(`src/features/automations/registry.ts`). id 는 builder 판단(예: `sms-sender-request-notify`).
  - `cadence: "hourly"`, `scheduleInfo: "5분마다 (cron-job.org)"` — `knowledge-index` 선례(5분 값이 없다. 미실행 판정이 느슨해질 뿐 오탐은 없다).
  - `cooldownMinutes` 는 수동 실행 버튼에만 걸린다(`actions.ts`). 작게(예: 1).
- cron-job.org 가 `POST /api/automations/run?jobId=<id>` (Bearer `CRON_SECRET`)를 5분마다 부른다. 이 경로라 `recordAutomationRun`·실패 알림·일일 보고·토글 OFF 시 skipped 를 그대로 얻는다. **전용 라우트를 만들지 않는다** — open-notices 처럼 `automation_runs` 사각지대가 된다.
- 5분마다 `automation_runs` 에 한 줄씩(하루 288줄) 쌓인다. `knowledge-index`(10분)와 같은 성격이라 받아들인다.

## 8. 설정 (env)

| env | 값 |
|---|---|
| `SHAREPOINT_SMS_REQUEST_SITE_ID` | 목록이 있는 사이트 id |
| `SHAREPOINT_SMS_REQUEST_LIST_ID` | 목록 id |
| `SMS_SENDER_REQUEST_MANAGER_EMAIL` | 담당 매니저 메일(= 보내는 메일함, 새 신청 받는 사람) |

- 실제 값은 이 문서·코드·커밋에 쓰지 않는다.

## 9. 코드 밖 체크리스트 (머지 전후)

1. **머지 전** Supabase SQL Editor 에 마이그레이션 적용(사용자). 적용 후 service_role 로 빈 표 조회 확인.
2. Vercel env 셋 추가 — **stdin 으로 넣지 않는다**(끝 줄바꿈이 값에 저장된다). `vercel env pull` 로 대조, 그 뒤 redeploy.
3. 머지·배포 직후 자동화 페이지에서 **수동 1회 실행** → `처음 실행 — 기존 N행 적재, 발송 없음` 확인. (자동 실행 토글이 켜져 있으면 수동 실행 버튼이 숨으므로 이 순서다.)
4. 자동화 페이지에서 그 잡의 **자동 실행 토글 ON**. 켜지 않으면 cron 이 5분마다 `skipped` 만 남긴다(`getJobEnabled` 기본 false).
5. cron-job.org 에 5분 간격 등록. 다음 실행이 `변화 없음` 으로 찍히는지 확인.
6. 라이브: 시험 신청 1건 → 5분 안에 매니저 메일 → 그 행을 '완료'로 → 5분 안에 신청자 메일 → 시험 행 삭제. 매니저 메일함 발송이 403 이면 Exchange Application Access Policy 확인(관리자 작업).
7. 사용자가 시험 중 만든 Teams 워크플로가 남아 있으면 끈다(중복 알림).
8. CLAUDE.md 자동화 잡 표에 한 줄 + `failed` 로 굳은 알림을 다시 보내는 법(해당 칸을 SQL 로 `pending`·시도 0 으로 되돌린다) 한 줄. 화면이 없어 이것이 유일한 재발송 경로다.
