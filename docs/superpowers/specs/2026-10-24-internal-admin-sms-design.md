# 프로젝트 > 내부관리자 — SMS 발신번호 사전등록 현황을 웹에서 본다

> 근거: Report 세션 인계 문서(`design-ref/internal-admin-sms/handoff.md`, gitignore) · 1차 시안(`design-ref/internal-admin-sms/mockup-v1.html`, https://claude.ai/artifact/UWRiiLmwVbFK8Hq5dFcZFw)

**질문**: 101개 학교·592회선의 사전등록 현황(SharePoint xlsm + 학교별 통합 PDF)을 엑셀을 열지 않고 웹에서 찾아보고, 나중에는 추가 제출 서류까지 웹에서 처리할 수 있게 하려면 무엇을 어떤 순서로 만드나.
**날짜**: 2026-10-24

## 1. 한 줄 결론

`/dashboard/internal-admin` 에 전용 페이지를 만들고, 페이지 안 탭 한 줄(개요·학교·발신번호·추가 제출·확인 필요)을 둔다. **1단계(이번 PR)는 읽기 전용** — xlsm 숨김 시트 4개와 `03. 학교별 제출 서류` 폴더 목록을 Graph 로 읽어 10분 캐시하고, 학교·발신번호·확인 필요 탭을 보여 준다. 보기는 **admin 과 지정한 운영자만** 한다. 추가 제출 처리(쓰기)와 책갈피는 별도 PR.

## 2. 지금

- 사이드바 `프로젝트 > 내부관리자`(slug `internal-admin`)는 `[slug]` catch-all 이 `ProjectPattern` 목업(`_data/patterns.ts` makeProject)을 그린다. 실제 데이터가 없다.
- 현황은 SharePoint `ApplyService2 / 문서 / 내부관리자/01. SMS 발신번호 사전등록/` 의 xlsm(VBA, 하이퍼링크로 시트 간 이동)으로만 본다. 담당자가 엑셀을 열어 검색칸에 학교명을 넣어야 한다.

## 3. 확정 입력 (조사 대상 아님)

- 탭은 한 줄: `[개요] [학교] [발신번호] [추가 제출] [확인 필요]`. 사이드바 계층은 늘리지 않는다.
- 데이터 원본은 당분간 xlsm. 웹이 쓰는 건 추가 제출 처리 때뿐(2단계).
- 추가 제출 처리 순서: 가림 → 사람 확인 → 통합 PDF 정해진 자리에 끼우기/교체 → 원본 99 보관 → xlsm 갱신.
- xlsm 은 몇 분 단위 캐시 + 화면에 기준 시각 표시. 이번 PR 은 1단계까지.

## 5. 라우트·탭·권한 경계

- 라우트 `/dashboard/internal-admin?tab=overview|schools|numbers|submissions|checks`, 기본 `schools`(모르는 값도 기본). `components/common/PageTabs` 사용(work-assignment 와 같은 방식).
- 1단계 탭: 개요·학교·발신번호·확인 필요. `추가 제출` 탭은 2단계에서 붙인다(1단계에선 탭을 안 보인다 — 비어 있는 탭을 두지 않는다).
- **보기**: **admin + 지정한 운영자만.** 로그인 사용자 전원이 아니다(사용자 결정, 2026-10-26).
  - 구현: '지정자 전용 메뉴' 집합을 새로 둔다. `src/app/dashboard/_data/sidebar-helpers.ts` 의 `ADMIN_ONLY_MENU_SLUGS` 옆에 같은 모양으로 두고 `internal-admin` 을 넣는다.
  - 판정(`canViewMenu`): admin 은 항상 true. 그 외는 이 집합의 slug 일 때 **`operator.allowedMenus` 에 그 slug 가 있어야** true. 이 집합 밖 메뉴의 판정은 지금과 동일하다 — 기존 `allowed_menus` 값이 다른 메뉴를 숨기지 않는다.
  - 가드 3곳: 사이드바(`filterSidebarSections`) · 라우트(`requireMenu`) · 2단계 server action 의 재판정. 한 곳만 막으면 메뉴는 숨었는데 주소로는 열린다.
  - 권한 부여: DB 직접 1회 — 지정할 운영자의 `operators.allowed_menus` 에 `internal-admin` 을 추가한다(§11). 조직권한 화면의 체크칸은 비범위, 필요해지면 별도 작업.
  - 화면 데이터는 학교명·대표번호·서류 O/✕ 수준이고, PDF 는 SharePoint 링크라 열람은 SharePoint 권한이 다시 막는다. 앱 판정은 그 앞의 첫 번째 문이다.
- **처리(2단계)**: 보기와 같은 명단(admin + `allowed_menus` 에 `internal-admin` 이 있는 운영자). 서버 action 이 다시 판정한다.

## 6. 화면

### 6.0 공통
- 헤더 부제: `현황 파일 _261017.xlsm · 기준 HH:mm` + `새로고침`(캐시 무효화 server action) + `서류 기준` 버튼(05 시트 내용 → `ModalShell`).
- 05 시트는 자주 안 바뀌는 기준표라 1단계는 **읽어서 그대로** 표로 보인다(가공하지 않음).
- 날짜는 `kstFormat`, 숫자는 `tabular-nums`, 행 호버·선택은 표준(`hover:bg-line-soft`, vermilion 선택).

### 6.1 개요
- 기존 `ProjectPattern`(목업 데이터) 그대로.

### 6.2 학교
- 구분 카드 4장(`KpiCard`: 4년제·전문대학·대학원·초중고 — 곳/회선/서류 미비/확인). 카드 클릭 = 구분 필터(`?gubun=`), 00 요약 시트 대체.
- 필터 줄: 학교 검색(`ListSearch`) · 단계 · 서류(완비/미비/확인 안 됨) · 확인 필요만.
- 표: 학교명 · 구분 · 단계 · 회선 · 서류 8칸 점(O/✕/대체/빈칸) · 확인 · PDF.
- 행 클릭 → `InspectorPanel`: 서류 8종 상태 + 미제출 사유 · 통합 PDF 열기(사본 폴더가 둘이면 둘 다) · 발신번호(최대 10줄 + '발신번호 탭에서 전체 보기' = `?tab=numbers&q=학교명`) · 이 학교 확인 필요 항목.
- 필터·선택은 URL 파라미터(새로고침·링크 공유에 살아남게).

### 6.3 발신번호
- 큰 검색창: **하이픈·공백 무시** 부분 일치(`0221644000` 으로 `02-2164-4000` 찾기), 학교명도 같은 칸.
- 필터: 상태(일괄 등록/추가 등록/서류 미비) · 구분.
- 표: 발신번호 · 학교 · 상태 · 등록일 · 제출 서류 · 비고. Moa 열은 3단계(권한 문제로 목록 미확보).
- 595행(실측일 기준) — 페이지네이션(`ListPagination`, 50행).

### 6.4 확인 필요
- 표: 유형 · 대상 · 내용 · 근거 · 할 일. 유형 필터.
- 대상 첫 줄이 학교와 맞으면 링크 → `?tab=schools&school=No`.
- **건수는 `_확인` 시트의 데이터 행 수로 센다.** `00. 요약` 의 '확인 필요 N건'은 수식이 아니라 손으로 적은 값이라 읽지 않는다(§14 '답한 질문' 4).

## 7. 데이터 계층 (`src/features/sms-sender/`)

- `source.ts` (server-only): 최신 xlsm 고르기(`_\d{6}\.xlsm$` 로 끝나는 이름 중 최신 날짜) → 4시트 usedRange(valuesOnly) + `03` 폴더 재귀 목록. 결과에 파일명·`lastModifiedDateTime`·읽은 시각.
- `parse.ts` (순수 함수, 테스트 대상): 헤더 이름으로 열 찾기(위치 고정 금지 — 열이 끼면 조용히 틀린다), 행 → `School` / `SenderNumber` / `CheckItem` / `DocStatus`, PDF 목록 → 학교별 단계·링크(경로로 판정: `제출완료/*` > `완료/검토완료` > `진행 중`), 별칭 적용, 하이픈 제거 정규화.
- `aliases.ts`: PDF 이름 → xlsm 이름 6줄(사람이 확인한 것만, 아래 표).
- `queries.ts`: react `cache()` + 모듈 TTL 10분(`payment-dates` 와 같은 모양) + `refreshSmsSenderCache` action.
- 헤더가 바뀌어 필수 열을 못 찾으면 **빈 표가 아니라 오류 화면**(어느 시트의 어느 열인지). xlsm 은 사람이 손으로 고치는 파일이라 이게 가장 흔한 고장이다.
- DB 테이블·마이그레이션 없음.

## 11. 코드 밖 등록 체크리스트
- Azure AD 앱의 기존 `Sites`/`Files` 읽기 권한으로 실측 완료 — 추가 등록 없음.
- **머지 후, 사용자 승인 하에 DB 직접**: 지정한 운영자의 `operators.allowed_menus` 에 `internal-admin` 을 추가한다. 이걸 안 하면 admin 말고는 아무도 메뉴를 못 본다(에러 없이 사이드바에서 빠질 뿐이다). 적용 뒤 지정자 계정으로 메뉴가 보이는지, 미지정 계정으로 주소를 직접 열면 막히는지 둘 다 확인한다.

## 12. 리스크
- **사람이 xlsm 구조를 바꾼다** → 헤더 이름 기반 + 못 찾으면 오류 화면(§7).
- **새 현황 파일 이름이 규칙을 벗어난다**(`SMS 발신번호 사전등록 현황_261017(수정).xlsm` 등, `_\d{6}\.xlsm$` 로 안 끝남) → 규칙 밖이면 무시하지 말고 기준 바에 '규칙 밖 파일 N개' 표시.
- **캐시 10분 동안 옛 값** → 기준 시각 + 새로고침 버튼.
- **`고를 값` 열(U)은 행 데이터가 아니다** — 드롭다운 목록이라 행과 무관한 값이 같은 줄에 있다(`_학교` 2행 `구분=4년제`, U=`전문대학`). 열을 위치로 읽다 U를 집으면 구분이 틀린다 → 헤더 이름 기반 + 테스트로 고정.
- **권한 부여를 빠뜨린다** → 지정 전에는 admin 만 본다. 에러가 아니라 '메뉴가 없다'로 나타나므로 §11 체크리스트에 확인 절차를 둔다.

## 14. 질문

### 답한 질문 (2026-10-26)

1. **두 폴더에 다 있는 43곳**: 같은 파일(해시·크기 동일)이 3곳(동양미래대학교·춘천교육대학교·한동대학교), 다른 판이 40곳이다. 다른 40곳 중 36곳은 `제출완료` 쪽이 최신이고 4곳(부산가톨릭대학교·세종대학교·영산대학교·호남대학교)은 `검토완료` 쪽이 최신이다. 보통 `제출완료`가 28~45KB 크고(표지·스탬프로 보인다) 검토완료 직후 같은 날 저장됐다. 예외는 숭실 +2.3MB · 한양여자 +2.7MB · 중부 +7.4MB · 한국항공 +0.67MB · 영산 −0.75MB · 조선 −2.67MB · 서일 −154KB · 부천 −62KB. → 1단계 결론 유지: 단계 = 가장 앞선 폴더, 다른 폴더 사본도 상세에 함께 표시. 어느 쪽에 끼울지는 아래 열린 질문으로 남는다.
2. **PDF 이름 6건 별칭**: §7 표로 확정. 한양대학교는 PDF 안의 사업자등록증 소재지(서울 성동구)와 재직증명서 소속('서울')이 두 사본 모두 서울이라 `(서울)` 로 묶는다. 동국대학교는 사업자등록증 소재지(서울 중구)가 근거 한 장뿐이다. 별칭 적용 뒤에도 **PDF 없는 학교 약 12곳**: 가톨릭대학교성의교정 · 서울대학교 · 을지대학교 · 신한대학교 대학원 · 한서대학교 · 중원대학교 · 단국대학교 대학원 · 성균관대학교 대학원 · 성신여자대학교 외국인 · (사)대한병원관리자협회 · 인천과학예술영재학교 · 한양대학교(ERICA). **한양대학교(ERICA) 는 'PDF 없음'으로 보인다.**
3. **보기 권한**: admin + 지정한 운영자만(사용자 결정). §5.
4. **'확인 필요 23건'**: `00. 요약` 의 23 은 수식이 아니라 손으로 적은 값(A50 문자열·B64 숫자)이고, `_확인` 은 지금 23행이라 현재 파일에서는 일치한다. 앞서 22행으로 적은 것은 셈 착오였다. 요약 시트는 갱신되지 않을 수 있으므로 화면 건수는 `_확인` 행 수로 센다(§6.4).
