# 에이전트 조직 — 파이프라인 4단계 + 조율

**질문**: 운영부 상황실 기준으로 에이전트 조직을 어떻게 구성하고, 그것을 어떤 화면으로 보나.
**날짜**: 2026-08-13

> **범위**: 이 문서는 **조직(組織) 화면 하나**를 다룬다. 첨부 참고 화면의 4탭(조직·현황·에이전트·채널) 중 **조직만** 만든다. 나머지 세 탭은 §6에서 왜 지금 안 만드는지 밝힌다.
>
> **함께 보는 문서**
> - `2026-08-10-assistant-system-agent-design.md` — 조율팀(어시스턴트)의 본체 설계
> - `2026-08-12-resident-agent-design.md` — 팀장에게 판단을 얹는 방법, `agent_traces`
> - `2026-08-12-knowledge-system-design.md` — 두 트랙이 공유하는 지식층

## 1. 왜 만드나

지금 자동화 잡이 **17개**다. 사이드바 `자동화실행`에 목록으로는 있지만, **무엇이 무엇을 위해 도는지 묶여 있지 않다.** 운영자가 보면 열일곱 줄의 평면 목록이고, 새로 온 사람은 어디서부터 읽어야 할지 모른다.

에이전트 조직은 그 열일곱을 **일의 흐름으로 묶어 보여준다** — 밖에서 가져오고(수집), 뜻을 가리고(판단), 사람에게 닿게 하고(전달), 그 전체를 지켜본다(관측). 여기에 운영자와 대화하는 조율이 하나 붙는다.

**이건 장식이 아니다.** §3에서 밝히듯 팀장은 실제 구현 대상이고, 조직 구조가 그 구현 순서를 정한다.

## 2. 조직

### 팀 경계 — 파이프라인 단계

| 팀 | 하는 일 | 팀장 | 왜 이 사람인가 |
|---|---|---|---|
| **수집팀** | 밖 → 안 | **지성** | 두 개의 심장 — 90분 내내 온 그라운드를 돈다 |
| **판단팀** | 안 → 뜻 | **성용** | 중원에서 각을 읽고 어디로 갈지 정한다 |
| **전달팀** | 뜻 → 사람 | **강인** | 킥이 정확하다 — 원하는 발밑에 꽂는다 |
| **관측팀** | 전체를 본다 | **현우** | 골문 뒤에서 전체를 보고 먼저 소리친다 |
| **조율** | 사람과 대화 | **명보** | 감독 — 누구를 언제 넣을지 정한다 |

팀장 이름은 **성을 뺀 이름만** 쓴다. 사내 별칭으로 읽히게 하려는 것이고, 실존 인물을 그대로 지칭하지 않기 위해서다.

조율만 **감독**이고 나머지는 **선수**다. 팀장이 자기 팀원을 돌리고, 감독이 팀장들에게 오더하는 구조가 그대로 맞는다.

### 팀별 구성

`✦` = 지금 LLM으로 판단하는 곳(3개). `—` = 잡이 없는 자리(준비 중).

#### 판단팀 · 성용
`대조` `근거우선` `의심` `예외기억`

#### 관측팀 · 현우
`무소식감지` `소음억제` `비용추적` `조용함`

| 역할 | 에이전트 | 출처 |
|---|---|---|

#### 조율 · 명보
`확인게이트` `권한분리` `모르면모른다` `대신실행`

팀원 없이 **직접 수행**한다. 운영자 질문을 받아 어느 팀의 일인지 정하고, 승인받아 대신 실행한다. 현재 준비 중 — 본체 설계는 `2026-08-10-assistant-system-agent-design.md`.

### 배치 검증

자동화 잡 **17개가 전부** 배치됐다. 남는 잡도, 두 팀에 걸친 잡도 없다. 이 불변식은 §4의 테스트가 강제한다.

### 조직에 넣지 않는 것

**사람이 버튼을 눌러 나가는 메일**(인수인계 요청·백업 요청·자료 요청)은 넣지 않는다. 스케줄로 도는 것이 아니라 운영자가 마법사에서 직접 보내는 것이라, 에이전트가 아니라 **사람의 도구**다. 조직도에 섞으면 "이건 누가 하는 일인가"의 답이 흐려진다.

## 3. 팀장이 실제로 하는 일 — 지금은 아무도 안 한다

**현재 팀장 역할은 cron이 하고 있다.** 시각이 되면 실행하고, 결과를 보지 않는다.

| | 지금 (cron이 팀장) | 팀장을 세우면 |
|---|---|---|
| 언제 도나 | 정해진 시각 | 같음 |
| 무엇을 시키나 | 항상 전부 | 오늘 필요한 것만 |
| 결과를 보나 | 성공/실패만 | 무엇이 나왔는지 읽고 다음을 정함 |
| 사람에게 | 전부 보고 | **볼 것만 골라서** |

관측팀장이 생기면, 지금처럼 17줄을 나열하는 대신 이렇게 된다:

> 입금 매칭이 3일째 같은 지점에서 실패합니다. 메시지가 매번 `504 MaxRequestDurationExceeded`로 같은데, 워크북 세션 만료 패턴입니다. 나머지 16개는 정상입니다. **오늘 볼 것은 이 하나입니다.**

**그래서 팀장은 페르소나 장식이 아니라 구현 대상이다.** 다만 다섯을 한 번에 세우지 않는다 — `2026-08-12-resident-agent-design.md`가 "one workflow, one channel, one reviewer for the first two weeks"를 근거로 하나씩 올리라고 결론냈고, 첫 대상으로 **관측팀장(digest)**을 골라뒀다. 읽기 전용이고, 데이터가 이미 있고, 매일 본인이 읽어 검증되기 때문이다.

**이 화면은 그 순서를 눈에 보이게 만든다** — 어느 팀에 아직 팀장이 없는지가 카드에 드러난다.

## 4. 진실 원천 — 조직도가 현실과 갈라지지 않게

### 어디에 두나

```
src/features/agent-org/
  registry.ts     팀 정의 (팀장·성향·팀원). 유일한 편집 지점
  types.ts        AgentTeam / AgentMember
  __tests__/      갈라짐 방지 테스트 3개
```

```ts
{
  id: "collect",
  name: "수집팀",
  leader: { name: "지성", tagline: "두 개의 심장 — 90분 내내 온 그라운드를 돈다" },
  traits: ["완주", "빠짐없이", "현장확인", "반복내성"],
  members: [
    { role: "마감", agent: "closing-scraper", jobId: "closing-scrape" },
  ],
}
```

**팀원의 출처는 셋 중 정확히 하나다.** 빠뜨리거나 두 개를 같이 적으면 테스트가 잡는다.

| 출처 | 뜻 | 화면 |
|---|---|---|
| `jobId: "..."` | 자동화 잡 | 잡 라벨 (레지스트리에서 조회) |
| `module: "..."` | 잡이 아닌 상시 동작 코드 | 모듈 경로 + `상시` |
| `planned: true` | 아직 없음 | `준비 중` 배지 |

`failure-watcher`가 `module`인 이유: 실패 알림은 cron 잡이 아니라 `recordAutomationRun`이 기록 직후 판정하는 **상시 동작**이다. 이걸 `planned`로 두면 **돌고 있는 것을 안 돈다고 표시**하게 된다.

**잡의 라벨·설명을 여기 복사하지 않는다.** `automations/registry.ts`에서 `jobId`로 찾아 렌더한다. 복사하면 잡 설명을 고칠 때 두 곳이 되고, 한쪽만 고쳐진다 — 오늘 팀 값에서 겪은 것과 같은 실패다(`2026-08-13` #963).

### 테스트 3개 — 이게 이 설계의 핵심이다

| 테스트 | 막는 것 |
|---|---|
| 모든 `jobId`가 자동화 레지스트리에 실재 | 오타·삭제된 잡을 가리키는 유령 팀원 |
| **모든 잡이 정확히 한 팀에 속함** | 잡을 추가하고 조직도에 안 넣는 것 |
| 에이전트 이름이 전 팀에서 유일 | 같은 이름이 두 자리에 |
| 팀원마다 출처가 정확히 하나 | `jobId`와 `planned`를 같이 적거나 셋 다 빠뜨리는 것 |

두 번째가 핵심이다. 이게 없으면 **몇 달 뒤 이 화면이 거짓말이 된다** — 잡은 늘었는데 조직도는 그대로이고, 아무 자동 검사도 그걸 못 잡는다. 오늘 하루에만 같은 구조의 사고를 세 번 겪었다(날짜 입력·버튼 표준·팀 값). 전부 "타입 검사도 CI도 통과하는데 화면만 틀린" 종류였다.

**역검증까지 한다** — 잡을 하나 추가하고 팀에 안 넣었을 때 실제로 실패하는지 확인한다. 통과만 본 가드는 아무것도 지키지 않는다.

## 5. 화면

### 위치

사이드바 `AI & 자동화` 그룹, **`자동화실행` 바로 위**. slug `agents`, 라벨 `에이전트`.

**전원 열람**한다(`adminOnly` 아님). 읽기만 하는 설명 화면이고, 운영자가 "이건 누가 하는 일이지"를 알 수 있어야 쓸모가 있다. 자동화실행이 admin 전용인 것은 **실행이 quota를 쓰기 때문**이지 목록이 비밀이어서가 아니다.

`page-meta-config.ts`:
```ts
agents: {
  headline: { accent: "AI & 자동화", title: "에이전트" },
  description: "운영 자동화를 파이프라인 네 단계로 묶어 봅니다. 무엇이 무엇을 위해 도는지 한눈에 봅니다.",
}
```

### 카드 격자

**인사이트 영상 카드(`VideoGrid.tsx`)와 같은 규격**을 쓴다. 이 레포에 이미 있는 유일한 카드 격자 선례이고, 마침 3열이라 참고 화면과 모양이 거의 같다.

```
grid grid-cols-1 gap-5 md:grid-cols-2 lg:grid-cols-3
카드: border border-line bg-situation-bg
```

카드 내부:

```
┌──────────────────────────────┐
│ ● 판단팀              성용     │
│ 중원에서 각을 읽고             │
│ 어디로 갈지 정한다             │
│ [대조][근거우선][의심][예외기억] │
│                              │
│ 팀원                          │
│ 세팅  ratio-auditor        ✦ │
│       경쟁률 세팅 점검         │
│ 링크  page-checker           │
│       경쟁률 페이지 점검       │
│ 입금  deposit-matcher        │
│       입금 매칭 자동화         │
└──────────────────────────────┘
```

### 배지를 새로 만들지 않는다

**`준비 중`만 배지로 쓴다**(공통 규칙상 대기 = 회색). 잡·모듈로 실재하는 팀원은 이름만 적고 배지를 안 붙인다. LLM으로 판단하는 곳은 `✦` 기호 하나.

오늘 배지 규칙을 정리한 직후라(#953·#954·#964) 새 라벨을 늘리지 않는다. 라벨이 하나 늘 때마다 `badge-tone.ts`의 규칙 순서를 다시 봐야 하고, 실제로 `성공`을 규칙에 안 넣어 `실패` 옆에서 회색이 될 뻔했다.

### 성향 칩

읽기 전용 라벨이다. **인터랙션 표준(호버·선택)을 적용하지 않는다** — 누를 수 없는 것에 호버 색을 주면 누를 수 있는 것처럼 보인다.

### 색

하드코딩 금지. `bg-situation-bg` / `border-line` / `text-ink` / `text-muted` 토큰만 쓴다.

## 6. 지금 안 만드는 것

| 안 만드는 것 | 왜 |
|---|---|
| **현황 탭** | 넣을 데이터가 없다. `agent_traces`가 아직 없어 토큰도 판단 근거도 기록되지 않는다 |
| **에이전트 탭** (개별 카드) | 조직 카드가 이미 전원을 보여준다. 팀원이 지금 17명이라 별도 목록이 줄 게 없다 |
| **채널 탭** | Teams 경로는 두 개뿐이고(실패 즉시 / 일일 보고) 이미 `CLAUDE.md`에 적혀 있다 |
| **카드 클릭 → 자동화 화면** | 자동화 페이지가 잡별 딥링크를 받는지 미확인. v1은 정적 |
| **팀장 구현** | 별개 작업. 첫 대상은 관측팀장(digest) — `2026-08-12-resident-agent-design.md` 1단계 |

빈 탭 세 개를 먼저 만들면 그게 부채가 된다. **관측이 생기면 그때 탭을 붙인다.**

## 7. 단계

### 1단계 — 조직 화면 (이 문서의 범위)
`agent-org/registry.ts` + 카드 격자 + 사이드바·메타 등록 + 갈라짐 방지 테스트 3개.

- **완료 조건**: 잡을 하나 추가하고 팀에 안 넣으면 **테스트가 실패한다**(역검증으로 확인). 17개가 전부 카드에 보인다
- **하지 말 것**: 탭. 팀장 구현. `agent_traces`

### 2단계 (별개 작업) — 관측 계기
`agent_traces` 신설 + 기존 LLM 3곳에 트레이스 기록. `2026-08-12-resident-agent-design.md` 0단계 그대로.

- **완료 조건**: 어제 `team-briefing`이 토큰을 얼마 썼는지 화면에서 답할 수 있다

### 3단계 (별개 작업) — 관측팀장
`automation-digest`가 나열 대신 판단한다. 2단계 계기에 트레이스가 자동으로 잡힌다.

- **완료 조건**: 2주간 매일 돌고, **"오늘 볼 것 없음"이 실제로 나온 날이 있다**

1단계만 이 문서로 구현한다. 2·3단계는 이미 별도 설계가 있으므로 여기서 되풀이하지 않는다.

## 8. 열린 질문

1. **팀이 늘어날 때 팀장 이름을 어떻게 정하나** — 지금은 축구로 묶여 있다. 여섯 번째 팀이 생기면 같은 계열에서 고르는 규약을 registry 주석에 적어둘지
2. **성향 칩이 실제로 쓰이나** — 지금은 설명용이다. 나중에 팀장 프롬프트의 성격 지시로 이어질 수 있는데, 그때 이 문자열을 그대로 쓸지 별도로 둘지
3. **`✦`(LLM 판단) 표시를 손으로 적나** — 지금은 registry에 직접 적는 방식이다. 잡이 LLM을 쓰는지 코드에서 도출할 방법이 마땅치 않은데, 손으로 적으면 §4가 막으려던 갈라짐이 여기서 다시 생긴다. 3개뿐이라 우선 손으로 두되, 늘어나면 재검토
