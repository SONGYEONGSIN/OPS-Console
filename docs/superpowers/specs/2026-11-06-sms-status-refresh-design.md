# SMS 발신번호 현황 파일 최신화 + 제출 서류 업로드 알림 — 설계

작성 2026-11-06. 사전 조사: 세션 scratchpad `status-refresh-recon.md`(읽기 전용 조사, 개인정보 없음).

## 1. 왜

내부관리자 > SMS 발신번호 등록 화면은 Teams 의 `SMS 발신번호 사전등록 현황_261017.xlsm`(이하 **현황 파일**)을 읽어 보여 준다.
그런데 현황 파일을 최신으로 만드는 일은 전부 사람(과 일회성 스크립트)이 한다.

- 세종텔레콤이 새 발번 리스트를 **메일 첨부**로 보내면 사람이 받아 Teams 에 올린다.
- Moa 발신번호 목록·PIMS 목록과의 대조(06·07 시트)는 이번 주에 일회성 스크립트로 한 번 만들었다(그 스크립트는 지워졌다).
- 메일로 오간 내용(확인 필요·제출 서류 기준)은 사람이 읽고 손으로 옮겼다.
- 학교가 낸 PDF 의 서류 8종 판정은 에이전트가 1,454쪽을 한 번 분류한 결과가 마지막이다.

사용자는 화면의 버튼 하나로 이것을 최신화하고 싶어 한다. 그리고 학교별 제출 서류 폴더에 파일이 올라오면 **SMS 발신번호 등록 담당자**가 바로 알기를 원한다.

## 2. 사용자가 정한 것 (2026-11-06)

| 물음 | 결정 |
|---|---|
| 현황 파일 본체를 어디까지 자동으로 바꾸나 | **세종 리스트에서 나오는 열만 다시 계산하고, 사람이 쓴 열은 보존**. 06·07 대조 시트도 새로 만든다 |
| 메일 | **새 세종 발번 리스트 첨부는 Teams 에 자동 저장 + 새 메일은 AI 가 '확인 필요' 후보로 요약**. 현황 파일 반영은 사람이 확인한 뒤 |
| 제출 서류 PDF | **새로 들어오거나 바뀐 PDF 만** 서류 8종으로 판정해 그 학교 줄을 갱신 |
| 업로드 알림 받는 사람 | **SMS 발신번호 등록 담당자**(신청 알림을 받는 매니저와 같은 사람, env `SMS_SENDER_REQUEST_MANAGER_EMAIL`) |
| 업로드 알림 시점 | **5분마다**, 기존 신청 알림 잡(`sms-sender-request-notify`)에 단계로 붙인다 |
| 같은 최신화에서 찾은 새 세종 리스트 | **바로 반영**. 무엇이 바뀌었는지는 이력의 '바뀐 점'에 남긴다 |
| 담당자 본인이 올린 파일 | **알림에서 뺀다** — 올린 사람(`lastModifiedBy.user.email`, 새 파일이면 `createdBy`)이 담당자 메일과 같으면 기록만 하고 보내지 않는다 |
| 버튼 권한 | **admin 과 SMS 발신번호 등록 담당자**(로그인한 운영자 메일 = `SMS_SENDER_REQUEST_MANAGER_EMAIL`). 다른 사람에게는 버튼 없이 이력만 보인다. 누를 때마다 Moa 로그인 인증 문자가 1통 간다 |

## 3. 목표 / 비목표 / 실패로 볼 것

**목표**
- 버튼 한 번 → 메일 확인 · Moa 수집 · 현황 파일 갱신 · 새 PDF 판정이 차례로 돌고, 무엇이 바뀌었는지 화면에 남는다.
- 제출 서류 폴더에 새 파일이 생기면 5분 안에 담당자에게 메일이 간다.

**비목표**
- 현황 파일을 생성 스크립트로 통째로 다시 만드는 것. 사람이 28판까지 고친 파일이라 손 수정이 지워진다.
- 메일 내용을 현황 파일에 **자동으로** 써 넣는 것. 요약은 후보일 뿐, 반영은 사람이 한다.
- PIMS 목록 자동 수집. 출처 화면이 확인되지 않았다 — Teams `03. PIMS 등록 리스트` 의 최신 파일을 그대로 쓴다.
- 전체 PDF 재판정.

**실패로 볼 것 (돌아가도 실패)**
- 사람이 쓴 칸(담당자·비고·확인·원서접수·PIMS·제출 서류 메모)이 하나라도 지워지거나 다른 줄로 옮겨지는 것.
- 누가 파일을 열어 둔 사이 덮어써서 그 사람의 수정이 사라지는 것.
- 매크로(VBA)·이름 정의·숨김 시트·수식 뷰(01~04)가 깨지는 것.
- 같은 업로드 알림이 두 번 가거나, 처음 켤 때 기존 파일 수백 개 알림이 쏟아지는 것.
- 실패가 조용히 묻히는 것(자동화 실행 보고에 안 잡히는 것).

## 4. 전체 모양

```
[웹] 현황 최신화 버튼 ──insert──▶ sms_status_refresh_requests (pending)
                                          │ 5분 폴러가 claim
                                          ▼
[회사 PC] scripts/sms-status-refresh/  ── ① 메일 ② Moa ③ PDF ④ 현황 파일 ──▶ Teams
                                          │ 결과 보고(POST)
                                          ▼
[웹] 최신화 이력 · 바뀐 점 · 확인 필요 후보   +  automation_runs (일일 보고)

[Vercel 5분 cron] sms-sender-request-notify ── 신청 알림(기존) + 업로드 알림(신규) ──▶ 담당자 메일
```

회사 PC 에서 도는 이유: Moa 는 Cloudflare 가 데이터센터 IP 를 막고 SMS 2FA 가 붙는다. 현황 파일 저장은 openpyxl 재저장이 매크로·서식을 망가뜨려 **Excel COM** 이 필요하다. 둘 다 Vercel 에서 안 된다.

업로드 알림은 Vercel 에서 돈다: Graph 로 드라이브를 읽는 코드(`features/sms-sender/source.ts` `walkPdfs`)가 이미 서버에 있고, 5분 잡도 이미 있다.

## 5. 업로드 알림 (PR-1, 독립)

- 기존 잡 `sms-sender-request-notify` 에 두 번째 단계를 붙인다. 신청 단계가 실패해도 업로드 단계는 돈다(서로의 실패가 서로를 막지 않는다). 결과 메시지는 두 단계를 같이 적는다.
- 대상: `내부관리자/01. SMS 발신번호 사전등록/03. 학교별 제출 서류` 아래 **모든 파일**(PDF 만이 아니다 — "파일이 올라오면"). 하위 폴더 깊이는 `walkPdfs` 와 같은 한도.
- 새 테이블 `sms_sender_doc_upload_notices`: 드라이브 item id(PK) · 파일명 · 폴더 경로 · webUrl · 내용 해시(quickXorHash) · 처음 본 시각 · 상태(`seeded|skipped_self|pending|sent|failed|dry_run`) · 시도 횟수 · 오류 코드. RLS 는 신청 알림 테이블(`20261103_sms_sender_request_notices.sql`)과 같은 규칙.
- **새 파일 = 처음 보는 item id, 교체 = 같은 id 에 내용 해시가 바뀐 것**(§8). 같은 파일이 단계 폴더 사이를 옮겨 다니는 것(접수 → 검토완료)은 id·해시가 같으므로 알림이 아니다.
- 첫 실행은 기존 파일 전부를 `seeded` 로 적재만 하고 보내지 않는다(신청 알림과 같은 규칙).
- 담당자 본인이 올린 파일은 `skipped_self` 로 적재만 한다(§2).
- 한 번 실행에서 새 파일 여러 개는 **메일 한 통**에 묶는다: 학교(폴더) · 파일명 · 올라온 단계 폴더 · 링크. 제목 `[내부관리자] 학교별 제출 서류 N건 업로드`.
- 실패 재시도·`failed` 고착·claim 은 신청 알림의 store 규칙을 그대로 따른다. `MAIL_DRY_RUN` 존중.

## 6. 현황 최신화 (PR-2 ~ PR-4)

### 6.1 요청과 화면

- `sms_status_refresh_requests`: `ratio_audit_requests` 와 같은 모양(`pending → running → done|failed`, requested_by, message) + `result jsonb`(단계별 결과·바뀐 점·확인 필요 후보) + `watermark`(이번에 본 메일·PDF 의 기준 시각).
- 동시에 pending/running 은 1건만. 버튼은 그동안 '진행 중'으로 잠근다.
- 폴러 API `/api/sms-status-refresh/request`(GET claim / POST 완료, `Bearer CRON_SECRET`) — **`src/proxy.ts` PUBLIC_PATHS 등록 필수**. 완료 보고에서 `recordAutomationRun` 을 불러 일일 보고에 잡히게 한다. 자동화 레지스트리에는 `cadence: "manual"` 로 등록.
- 화면: SourceBar 에 `현황 최신화` 버튼(헤더 액션 버튼 표준). 그 아래 또는 모달로 **최신화 이력** — 언제·누가·각 단계 결과·바뀐 점 요약·확인 필요 후보. 실패면 이유를 사람이 할 일로 적는다("누가 파일을 열어 두었습니다. 닫고 다시 누르세요").
- 권한: 화면은 메뉴 가드(`requireMenu`). 버튼은 admin 또는 담당자(§2)만 보이고, server action 이 폼을 믿지 않고 DB 의 로그인 운영자로 다시 확인한다.

### 6.2 회사 PC 처리 순서

폴러 `scripts/sms-status-refresh/`(Python, `-I`), 작업 스케줄러 5분. 각 단계는 결과를 남기고, **앞 단계가 실패해도 뒤 단계 중 그 결과에 기대지 않는 것은 계속한다.** ④ 는 ①·② 의 결과 파일이 아니라 Teams 폴더의 **그 시점 최신 파일**을 읽으므로 ①·② 가 실패해도 지난 자료로 돈다(결과에 그렇게 적는다).

**① 메일** (Graph Application `Mail.Read`, 메일함 기능과 같은 토큰)
- 메일박스: env `SMS_STATUS_MAILBOX_UPN`. 폴더는 표시 이름 경로 상수 둘 — `받은 편지함/01. 결제사/세종텔레콤`, `받은 편지함/02.운영부/운영2팀/<세종 담당자 폴더명>`(폴더명은 env 로, 같은 경로에 사람 이름 폴더가 13개라 이름으로 고정).
- 지난 성공 실행의 watermark 이후 받은 메일만.
- 첨부 중 파일명이 발번 리스트 패턴(`발번\s*리스트`)인 것은 Teams `04. 발신번호 등록 리스트/01. 세종 등록 리스트` 에 원래 이름으로 저장(`conflictBehavior=fail`, 같은 이름이 이미 있으면 건너뛰고 결과에 적음).
- 새 메일들을 `claude -p`(격리 옵션 필수 — 어시스턴트 폴러와 같은 `strictMcpConfig`/`settingSources:[]` 규칙)로 '확인 필요' 후보로 요약: 유형 · 대상 학교 · 내용 · 근거(메일 날짜) · 할 일. `_확인` 시트와 같은 열. **현황 파일에는 쓰지 않는다.**
- 온라인 보관함은 Graph 로 닿는지 확인되지 않았다 — 새 메일만 보므로 이번 범위에서 필요 없다.

**② Moa** (`scripts/moa-closing/scrape.py` 의 `setup_driver`·`login_and_2fa` 재사용)
- SMS 우편함 소비자 이름 `sms-status-refresh` 를 `features/sms-codes/schemas.ts` 와 python env 양쪽에 추가. 리스가 점유 중이면(409) **폴백 없이 이 단계만 실패**로 적는다(마감·경쟁률 점검과 동시에 못 돈다). run-log 에 `(SMS: 우편함|make)`.
- 화면 `https://moa.jinhakapply.com/Message/CallBack`, 빈 조건 `Search()`, `table.tbl.type1` 전체(페이지네이션 없음). `SetCallBackUpdate` 는 절대 부르지 않는다(수정 함수).
- Teams `02. Moa 등록 리스트/Moa 등록 리스트_YYMMDD.xlsx` 로 저장(모든 칸 텍스트, 1행 추출 정보, 2행 헤더 — 11-04 파일과 같은 모양). 같은 날 두 번째면 이름에 `_2`.

**③ 제출 서류 PDF 증분 판정**
- 지난 성공 실행 이후 새로 생기거나 `lastModifiedDateTime` 이 바뀐 PDF 만.
- 쪽마다 서류 8종(`DOC_KINDS`)으로 분류 — 이전 판정(`doc_pages.json`)과 같은 분류 기준·프롬프트를 레포로 옮긴다.
- 결과는 그 학교의 서류 8종 표시·제출 상태·미제출 서류 계산에 쓴다. 판정 근거(파일·쪽)는 결과 jsonb 에 남긴다.

**④ 현황 파일 갱신**
1. 현황 파일을 내려받고 **eTag 를 기록**한다.
2. 최신 세종 리스트(파일명의 날짜 6자리로 고름)를 내려받아 openpyxl 로 **서식까지** 읽는다 — 상태는 번호 칸 바탕색이다(노랑 일괄 / 주황 추가 / 빨강 미비).
3. 새 값을 계산한다.
   - `_번호`: 세종 리스트 한 줄 = 한 행. 키는 **발신번호 숫자만**. 학교명·구분·발신번호·상태·등록일자는 다시 계산하고, **제출 서류·비고는 같은 번호의 기존 값을 그대로 옮긴다.** 세종에서 사라진 번호는 행을 빼고 '바뀐 점'에 적는다.
   - `_학교`: 키는 학교명(정규화). 등록 회선·일괄·추가·서류 미비·최근 등록일은 다시 계산하고, **담당자·원서접수·PIMS·제출 서류·확인·비고는 보존.** 세종에 새로 생긴 학교는 사람 칸을 비운 채 행을 추가하고 '바뀐 점'에 적는다.
   - `_서류`: 세종 등록 상태·등록 회선은 다시 계산. 서류 8종·제출 상태·미제출 서류는 ③ 에서 판정한 학교만 바꾸고 나머지는 보존.
   - `00. 요약`: 숨김 시트 집계로 다시 쓴다(지금은 생성 시점 고정값이라 숨김 시트를 고쳐도 안 바뀐다).
   - `06. Moa 대조` · `07. PIMS 대조`: 11-04 규칙 그대로(키 = 번호 숫자, 대학 보조 키 = ID 4자리, 결과 분류·열·요약 행 동일).
   - `_확인`·`05. 제출 서류 기준`: **건드리지 않는다**(메일 기반 수기, 후보는 화면에만).
4. **Excel COM 으로 써 넣는다**(openpyxl 재저장 금지). 숨김 시트 행 수가 바뀌면 01~04 수식 뷰가 그 범위를 따라가는지 확인(생성기 `layout.search_sheet()` 의 수식 규칙). 저장 후 `vbaProject.bin` 원본 바이트 복원(Excel 이 매크로 끈 채 저장하면 캐시가 빠진다).
5. **verify** — 11-04 의 18항목 검사를 이식: 손대지 않는 시트는 셀 단위(값+수식) 동일, 사람 칸은 키 기준으로 전후 동일, VBA 해시·모듈 소스, 이름 정의 `고를값_*`, 새 값은 계산 결과와 대조. 하나라도 어긋나면 **올리지 않는다.**
6. 기록한 eTag 로 **If-Match** 업로드. 412(그새 누가 저장) · 423(누가 열어 둠)은 정상 실패로 결과에 적고 끝낸다 — 다시 누르면 처음부터 새 파일로 한다.
7. 올린 뒤 앱이 읽는 시트를 다시 읽어 행 수를 확인한다. 화면 캐시는 결과 보고 때 무효화한다.

### 6.3 코드의 출처

## 8. 설계자 판단 (검토에서 나온 물음, 사용자 확인 전 기본값)

- **'사람 칸'의 정의.** 생성기가 계산해 넣은 칸(`_번호` 제출 서류·비고, `_학교` 제출 서류·확인·비고)도 그 뒤 사람이 고쳤을 수 있다. 같은 폴더의 생성기 산출물 `_261015.xlsm` 과 현재 파일을 칸 단위로 비교해 **값이 다른 칸 = 사람이 고친 칸**으로 보고 보존한다. 같은 칸은 계산 칸이므로 다시 계산한다(③ 결과·새 세종 비고가 반영되도록). 이 '고친 칸 목록'은 갱신 후 파일에 숨김 메타 시트 `_수정` 으로 남겨 다음 실행이 기준으로 쓴다.
- **번호로 못 잇는 행.** 번호 칸이 빈칸·범위(`~`)·글자인 행과 세종에 여러 줄인 번호는 `(Univ, 원문 번호 칸)` 으로 잇는다. 그래도 짝이 없으면 사람 칸을 옮기지 않고 '바뀐 점'에 "옮기지 못한 메모 N건(학교·원문)"으로 적는다 — 엉뚱한 줄로 옮기는 것보다 낫다.
- **PDF 판정 합치기.** 새 판정은 기존 표시에 **더하기만** 한다(OR). 자동으로 표시를 지우지 않는다. 같은 파일을 덮어쓴 새 판(교체)에서 전에 있던 서류가 안 보이면 지우지 않고 '확인 필요 후보'로 올린다.
- **첫 실행 기준점.** 단계별로 따로 둔다(메일·PDF 각자의 watermark). 처음엔 현황 파일이 Teams 에 생긴 **2026-10-17 00:00 KST** 부터 본다(그 전 메일·PDF 는 이미 손으로 반영된 것). watermark 는 그 단계 결과가 DB 에 저장되면 전진한다 — ④ 가 412/423 으로 실패해도 ③ 판정은 DB 에 남고, 다음 실행의 ④ 가 그것을 다시 적용한다(재판정 비용 없음).
- **요약 열람 범위.** `sms_status_refresh_requests` 는 RLS 로 직접 읽기를 막고(service_role 만), 화면은 `requireMenu` 를 통과한 서버 컴포넌트가 읽는다 — 지금 내부관리자 화면이 현황 파일 내용(번호 포함)을 보여 주는 것과 같은 경계다. 요약에는 번호·이름이 들어가도 된다(그래야 할 일을 할 수 있다). 로그·automation_runs 메시지에는 건수만.
- **덮어쓴 업로드.** 같은 item id 라도 `file.hashes.quickXorHash` 가 바뀌면 '교체'로 알린다. 폴더 이동은 해시가 같으므로 알리지 않는다. 테이블에 해시 칸을 둔다.
