# Teams 봇 — 채팅방에서 부르는 어시스턴트

## 1. 무엇을

운영부 그룹 채팅방과 팀 채널에서 `@어시스턴트` 로 부르면, 웹 어시스턴트와 **같은 답**이 그 자리에 붙는다.

## 2. 왜

지금 어시스턴트는 웹 화면에서만 쓴다. 그런데 운영자가 하루 종일 열어 두는 건 Teams다. 질문이 떠오르는 자리와 답이 있는 자리가 달라서, **묻지 않고 넘어가거나 옆 사람에게 물어본다.**

같은 질문이 채팅방에서 반복되는 것도 문제다. 웹은 1:1이라 답이 남지 않지만, 채팅방 답은 **여럿이 함께 본다.**

## 3. 창구는 이미 있다

`POST /api/assistant/bot` 이 질문을 웹과 **같은 큐**에 넣고, `GET` 으로 답을 돌려준다. 2026-08-26 실측:

| | |
|---|---|
| 비밀키 없음 | 401 |
| 명부 밖 사용자 | 403 — 비밀키만으로 사칭 불가 |
| 질문 → 답 | **6초**, 볼트 문서를 근거로 인용 |

**없는 것은 Teams 쪽 다리 하나뿐이다.**

## 4. 결정

### 4-1. 15초 안에 답할 수 없다

Teams 는 메시징 엔드포인트가 **15초 안에** 응답하기를 기대한다. 우리 어시스턴트는 6~40초다. 회사 PC 에이전트가 볼트를 하나씩 읽기 때문이고, 그게 이 어시스턴트의 값어치다.

그래서 **두 번 쓴다.**

1. 부르는 즉시 `찾아보는 중…` 을 채팅에 올린다 (activity id 를 받아 둔다)
2. 답이 준비되면 **그 메시지를 고쳐 쓴다** (`PUT .../activities/{id}`)

새 메시지를 또 붙이지 않는 이유: 채팅방은 여럿이 보는 자리라 봇이 두 줄씩 쌓으면 대화가 밀린다. 고쳐 쓰면 **한 줄로 끝난다.**

고쳐 쓰기가 실패하면(권한·시간 초과) 그때만 새 메시지로 붙인다 — 답이 통째로 사라지는 것보다 낫다.

### 4-2. 답을 기다리는 것은 누구인가

봇 서버(Vercel)는 **요청 하나를 붙들고 기다리지 않는다.** Vercel 함수는 실행 시간 제한이 있고, 40초를 붙들면 그동안 다른 질문을 못 받는다.

대신 `assistant_requests` 에 **어디로 답할지**를 함께 적어 두고, 별도 경로가 완료된 건을 Teams 로 보낸다.

```
Teams  ─@멘션→  /api/teams/messages  ─적재→  assistant_requests
                       └─즉시 "찾아보는 중" 게시 (activity id 저장)

회사 PC 에이전트 ─답─→ assistant_requests.status=done
                              ↓
                    /api/teams/flush  ─수정→  Teams 메시지
```

`flush` 는 cron-job.org 가 부른다(1분). **회사 PC 폴러가 직접 Teams 로 보내지 않는다** — 폴러는 볼트를 읽는 일만 하고, 채팅 발송 자격증명을 그 PC 에 늘리지 않는다.

### 4-3. 누가 물을 수 있나

`operators.email` 에 있는 사람만. 채팅방에는 운영부 아닌 사람도 있고, 어시스턴트는 인수인계·연락처 같은 **내부 기록**을 읽는다.

명부에 없으면 답하지 않고 **그 사실을 채팅에 적는다** — 조용히 무시하면 봇이 죽은 줄 안다.

### 4-4. 인증

Bot Framework 가 보내는 요청은 **JWT 로 검증한다.** 엔드포인트 주소는 공개돼 있어, 검증이 없으면 아무나 남의 이름으로 질문을 넣을 수 있다.

- 수신: `Authorization: Bearer` 의 토큰을 Bot Framework JWKS 로 검증(`iss`·`aud`=우리 App ID·`serviceUrl`)
- 발신: `login.microsoftonline.com/botframework.com` 에서 토큰을 받아 `serviceUrl` 로 POST

## 5. 자료 구조

`assistant_requests` 에 열 셋을 더한다. 별도 표를 만들지 않는 이유는 **같은 큐를 쓴다는 결정** 때문이다 — 표가 갈리면 상태가 두 벌이 된다.

| 열 | |
|---|---|
| `teams_conversation_id` | 어느 대화로 답할지 |
| `teams_activity_id` | 고쳐 쓸 메시지 |
| `teams_service_url` | 테넌트별로 다르다. 고정값으로 박으면 다른 지역에서 깨진다 |

셋 다 없으면 웹 요청이다 — `flush` 가 건너뛴다.

## 6. 단계

### T1 — 받는 쪽 (Azure 리소스 없이 가능)

- `POST /api/teams/messages` — Activity 수신, JWT 검증, 멘션 텍스트 정리, 적재
- `features/teams-bot/activity.ts` — 순수 함수: 멘션 제거·질문 추출·발신자 UPN 추출
- `features/teams-bot/jwt.ts` — 토큰 검증
- 마이그레이션: 위 열 셋

**이 단계는 App ID 없이도 다 만들고 테스트할 수 있다.** 검증만 실제 토큰으로 나중에 확인한다.

### T2 — 답하는 쪽

- `POST /api/teams/flush` (CRON_SECRET) — `status=done` 이고 `teams_activity_id` 가 있는 건을 수정 게시
- `lib/microsoft/bot-framework.ts` — 토큰 발급, 메시지 게시·수정
- 답이 길면 자른다 — Teams 메시지에는 상한이 있다

### T3 — Teams 앱 패키지

- `manifest.json` + 아이콘 2장(192·32) → zip
- 그룹 채팅(`groupChat`)·팀 채널(`team`) 범위로 선언
- 사용자 지정 앱 업로드로 설치 (이미 되는 것을 확인했다)

### T4 — 봇 등록

메시징 엔드포인트를 우리 주소로 걸고 Teams 에 연결한다. 길이 둘인데 **Azure 구독은 안 쓴다.**

| | Teams 개발자 포털 | Azure Bot 리소스 |
|---|---|---|
| 구독 | **불필요** | 필요 |
| 자리 | dev.teams.microsoft.com > 도구 > 봇 관리 | portal.azure.com |
| 범위 | 그룹 채팅·채널 모두 | 같음 |

2026-08-26 확인: 이 테넌트에는 **Azure 구독이 없다.** 목록이 비어 있고, 만들려면 계정
업그레이드(유료 전환)가 필요한데 청구 계정이 개인 이름으로 잡혀 있다 — 회사 봇을
개인 결제에 묶지 않는다. 그래서 **개발자 포털로 등록한다.**

아웃고잉 웹훅이라는 세 번째 길도 있지만 쓰지 않는다 — **팀 채널에서만** 동작해서
그룹 채팅방이 빠지는데, 그게 이번 요청의 절반이다.

## 7. 위험

- **15초** — 즉시 응답을 못 하면 Teams 가 오류를 띄운다. 적재는 빠르지만 JWT 검증이 네트워크를 타므로 JWKS 를 캐시한다
- **답이 영영 안 온다** — 회사 PC 가 꺼져 있으면 `찾아보는 중…` 이 그대로 남는다. `flush` 가 3분 넘은 건을 **안내 문구로 바꾼다**
- **채팅방은 공개된 자리다** — 명부 밖 사용자가 물으면 내부 기록이 새므로 발신자 검증이 핵심이다
- **`serviceUrl` 을 믿는다** — JWT 에 들어 있는 값과 대조한다. 안 하면 답을 남의 서버로 보내게 만들 수 있다

## 8. 여기서 다루지 않는 것

- 1:1 개인 채팅 — 이번 범위는 그룹방·채널이다
- 대화 이어가기(스레드 문맥) — 첫 판은 질문 하나에 답 하나
- 파일 첨부·카드 UI — 글로 답한다
