# 운영부 매뉴얼 — 반기 점검 알림 + 수정 알림 설계

작성 2026-11-09. 사전 조사: 세션 scratchpad `manual-ledger-recon.md`(읽기 전용, 개인정보 없음).

## 1. 왜

운영부 매뉴얼은 Teams `운영부/05. 매뉴얼` 폴더에 있고, 무엇을 누가 맡는지는 `00. 연간 운영부 업무 구성표_개편안_최종.xlsx` 의 `2. 매뉴얼 대장` 시트가 정한다. 지금은 매뉴얼을 제때 고치라고 알려 주는 장치도, 누가 고쳤는지 관리자가 아는 장치도 없다.

## 2. 사용자가 정한 것 (2026-11-09)

| 물음 | 결정 |
|---|---|
| 알림 대상 매뉴얼 | **진행 중 업무의 문서** — `2. 매뉴얼 대장` 행 중 업무가 `1. 연간 일정` 의 '진행 중' 구역에 있는 것(현재 37행). 상시 문서(연간 일정에 없는 업무)는 뺀다 |
| 정기 알림 시점 | **8월·3월 첫 영업일 10시**. 8월 = 1·2분기(4~9월), 3월 = 3·4분기(10~3월). 관리 가이드 시트의 '연 1회 6월'을 대신한다 |
| 정기 알림 형태 | 담당자별 한 통, **인라인 스타일 HTML**, 문서명을 누르면 그 파일이 Word Online 으로 바로 열린다 |
| 수정 알림 | 담당자가 매뉴얼을 고치면 **편집이 30분 멈춘 뒤 한 통** |
| 수정 알림 받는 사람 | **관리자 두 명**(env `MANUAL_EDIT_ADMIN_EMAILS`, 쉼표 구분) |
| 발신 메일함 | **받는 사람 본인 메일함 → 본인에게**(업무 안내 메일 `service-notice` 와 같은 방식, `senderUserId` = 수신자). 정기 알림은 각 담당자 메일함에서 그 담당자에게, 관리자 요약·수정 알림은 관리자마다 각자 메일함에서 각자에게 한 통씩 |

## 3. 목표 / 비목표 / 실패로 볼 것

**목표**
- 8월·3월 첫 영업일에 담당자마다 '내가 맡은 진행 중 매뉴얼' 목록 메일이 한 번 간다.
- 매뉴얼을 고치고 30분이 지나면 관리자 두 명에게 '누가 어느 문서를 고쳤는지' 메일이 간다.

**비목표**
- 엑셀(대장·가이드 시트)을 고치는 것. 읽기만 한다.
- 매뉴얼 내용 검토·요약.
- 화면(메뉴) 추가. 결과는 자동화 실행 기록과 일일 보고로 본다.

**실패로 볼 것**
- 같은 반기에 같은 담당자에게 정기 알림이 두 번 가는 것.
- Word Online 자동 저장마다 수정 알림이 가는 것.
- 담당자를 못 찾은 매뉴얼이 조용히 빠지는 것.
- 반기 잡이 일일 보고에서 '미실행'으로 오탐되는 것.

## 4. 원천 읽기 (두 기능 공용)

- 드라이브: 기존 `SHAREPOINT_DRIVE_ID`. 폴더: 기존 env `SHAREPOINT_MANUAL_ITEM_ID`(`/dashboard/manuals` 가 쓰는 것).
- 구성표 파일: 새 env `SHAREPOINT_MANUAL_LEDGER_ITEM_ID`(item id — 파일명에 '최종'·'개편안'이 붙었다 떨어지는 관행이라 경로로 찾지 않는다).
- `2. 매뉴얼 대장`: 헤더 행을 이름으로 찾는다(현재 4행, 열 `코드·구분·업무·종류·문서명·담당자·보관 위치·최종 수정·링크 상태·개정 이력 점검`). 헤더가 바뀌어 필수 열(업무·문서명·담당자)을 못 찾으면 **빈 결과가 아니라 실패**로 끝낸다. 시트는 번호를 뗀 이름으로 찾는다(2026-11-10 번호가 밀려 404 — 실측).
- `1. 연간 일정`: 구역 머리행(`▪ …`)으로 진행 중 / 진행하지 않는 사업 / 이관·중단을 가른다. '진행 중' 구역의 업무 이름 집합만 쓴다. 구역 머리행을 못 찾으면 실패. 시트는 번호를 뗀 이름으로 찾는다(2026-11-10 번호가 밀려 404 — 실측).
- 문서명 → 파일: 폴더 children 에서 **파일명 정확 일치**(같은 코드의 옛 버전이 섞여 있어 코드 접두로 맞추면 엉뚱한 파일이 걸린다). 못 찾은 문서명은 '연결 안 됨'으로 모은다.
- 링크: driveItem `webUrl`(파일명이 바뀌어도 유지되고 Word Online 으로 열린다).
- 담당자 → 메일: `operators.name` 정확 일치. 한 칸에 여러 명이면 구분자로 나눠 각자에게. 못 찾은 담당자(팀 이름·명단에 없는 사람)는 '담당자 미확인'으로 모은다.

## 5. 반기 점검 알림 (PR-A)

- 자동화 잡 `manual-review-reminder`, cadence `monthly`. cron-job.org 가 **매일 10:00 KST** 호출한다(`service-notice-mail` 과 같은 방식 — 반기 cron 두 번은 미실행 임계 840h 에 걸려 오탐).
- 보내는 날: 3월·8월이고 **그 달 첫 영업일**(`canSendOn` 의 주말·공휴일 판정 재사용)일 때만. 다른 날은 `skipped` 로 기록하고 끝.
- 반기 키: 8월 → `YYYY-H1`(그해 4~9월), 3월 → `(YYYY-1)-H2`(전년 10월~그해 3월). 날짜 계산은 KST 기준 함수 하나로, 테스트로 고정.
- 중복 방지: 이력 테이블 `manual_review_reminders`(반기 키 + 수신자 메일 유니크, 상태 `sent|failed|dry_run`). 이미 `sent` 면 건너뛴다. 실패한 수신자만 같은 날 다음 호출(없으면 다음 영업일까지 그 달 안)에서 재시도 — 그 달 첫 영업일이 지나도 그 달 안이고 아직 `sent` 가 아니면 보낸다.
- 메일(담당자별 한 통):
  - 제목 `[운영부] 매뉴얼 점검 안내 — {1·2분기(4~9월)|3·4분기(10~3월)}`
  - 본문: 인사 한 줄, "맡으신 진행 중 업무의 매뉴얼입니다. {달} 말까지 내용을 점검하고 바뀐 점을 반영해 주세요." 표(업무 · 문서명[링크] · 최종 수정일). 인라인 스타일만(Outlook 호환 — `open-notices/mail-html.ts` 의 규칙: `white-space: pre-wrap` 금지, 표는 table 태그).
  - 발신: 담당자 본인 메일함 → 본인(§2, `sendGraphMail` 의 `senderUserId` = 수신자 메일). `MAIL_DRY_RUN` 존중.
- 관리자 요약: 발송이 끝나면 관리자 두 명에게 한 통 — 보낸 담당자 수 · 매뉴얼 수 · **담당자 미확인 / 파일 연결 안 됨 목록**(조용히 빠지지 않게).

## 6. 수정 알림 (PR-B)

- 기존 5분 잡에 붙이지 않고 새 잡 `manual-edit-notify`(cadence `hourly` 미만이 없어 `hourly` 로 두고 cron-job.org 5분 호출 — 미실행 임계는 hourly 기준으로 충분).
- 감시 대상: §4 의 대장 행(진행 중 여부와 무관하게 **대장 49행 전부**의 연결된 파일) — 상시 문서도 고치면 관리자는 알고 싶다. 구성표 파일 자체는 뺀다.
- 감지: 폴더 children 1회(`lastModifiedDateTime`·`cTag`) → 지난번과 달라진 파일만 versions 조회 → 사람 편집자(`version.lastModifiedBy.user.email` 있음)만 센다. 메일 없는 버전(앱 기록)은 무시.
- 디바운스: 파일별로 '열린 편집 묶음'(첫 편집 시각, 마지막 편집 시각, 편집자 집합)을 둔다. **마지막 편집 후 30분** 동안 새 버전이 없으면 닫고 알림 대상에 올린다.
- 관리자 본인(두 명)만 고친 묶음은 알리지 않는다(기록만).
- 메일: 한 번 실행에서 닫힌 묶음을 한 통에 모아 관리자마다 **각자 메일함에서 각자에게**(§2). 한 관리자 발송이 실패해도 다른 관리자 발송은 진행하고, 실패한 쪽만 재시도한다. 제목 `[운영부] 매뉴얼 수정 {N}건`. 표: 문서명[링크] · 업무 · 담당자 · 고친 사람(operators 에 있으면 이름, 없으면 Graph 표시 이름) · 편집 시간대.
- 테이블 `manual_edit_watch`(파일 item id PK, cTag, 마지막 본 버전 id, 열린 묶음 jsonb, 상태) + `manual_edit_notices`(보낸 묶음 이력). claim·재시도·`failed` 고착·첫 실행 seeding(현재 상태를 기준으로 적재만, 알림 없음)은 업로드 알림(`sms-sender/upload-notify`)의 규칙을 따른다.

## 7. 개인정보·권한

- 테이블은 RLS 정책 0·service_role 전용. 메일 주소는 테이블에 남기지 않는다(반기 이력의 수신자 키는 예외 — 중복 방지에 필요, 화면 없음).
- 로그·자동화 실행 메시지에는 건수만.

## 9. 설계자 판단 (사용자 확인 전 기본값)

- 정기 알림의 '점검 기한'은 그 달 말일로 적는다.
- 수정 알림 감시는 진행 중만이 아니라 대장 전체(§6).
- 담당자가 둘인 행은 둘 다에게 보낸다.
- 반기 알림 재시도: 첫 영업일 이후 그 달 안의 매일 호출은 대장을 다시 읽어, 그 반기에 `sent` 가 없는 담당자에게 보낸다(첫날 실패한 사람 + 달 중간에 대장에 새로 들어온 담당자). 담당자 미확인 행은 메일 주소가 없어 재시도 대상이 아니다.
- 관리자 요약은 **반기마다 한 번**(첫 발송일). 같은 이력 테이블에 수신자 키 `__summary__` 행으로 중복을 막는다 — 그 달 내내 같은 미확인 목록이 매일 가지 않게.
- 정기 알림 표의 '최종 수정일'은 **대장의 `최종 수정` 칸 값 그대로**. 파일 메타데이터 시각은 11-08 앱 일괄 작업으로 거의 전부 같은 날로 찍혀 있어 오해를 부른다.
- 열린 편집 묶음의 편집자는 **operators id(있으면) 또는 Graph 표시 이름 + 관리자 여부 플래그**로 저장한다. 메일 주소는 남기지 않는다(§7).
- 일일 보고는 그날 실행 기록이 하나라도 있으면(스킵 포함) 미실행으로 보지 않으므로, 매일 호출 + 스킵 기록으로 충분하다(§5 의 cron 두 번 금지는 그대로).
